# ТЗ: демон управления роутером (backend)

Для Claude Code. Задача — написать Go-демон, управляющий сетевыми режимами домашнего роутера через единый HTTP API.

---

## 1. Целевая среда

| Параметр | Значение |
|---|---|
| Железо | GL-MT3600BE (Beryl 7) |
| ОС | OpenWrt 25.12.x, vanilla (не GL.iNet stock) |
| Архитектура | `aarch64_cortex-a53` |
| Пакетный менеджер | `apk` (не opkg) |
| Firewall | fw4 / nftables |
| Режим сети | подключение к внешнему WiFi как клиент, клиенты роутера за NAT |
| Светодиоды | `/sys/class/leds/blue:status`, `/sys/class/leds/white:status` |

Сборка: `GOOS=linux GOARCH=arm64 CGO_ENABLED=0`, `-ldflags="-s -w"`. Целевой размер бинаря — до 10 МБ. Никаких cgo-зависимостей.

## 2. Что уже работает на роутере

**Nikki (mihomo)** — прозрачный прокси, установлен вручную из GitHub Releases.
- Clash API: `http://127.0.0.1:9090`
- Профиль: mihomo-конфиг с `proxy-providers` типа `file`
- Файл провайдера: `/etc/nikki/run/providers/sub.yaml`
- Рабочий конфиг: `/etc/nikki/run/config.yaml` — **генерируется, править нельзя**
- Важно: mihomo не читает файлы провайдеров вне `/etc/nikki/run` (SAFE_PATHS)
- Группы в профиле: `PROXY` (url-test поверх провайдера) и `BYPASS` (fallback: `[PROXY, REJECT]`)
- Маршрутизация: в туннель уходят только Telegram, YouTube, Meta; всё прочее — `MATCH,DIRECT`
- Требование fail-closed: при недоступности прокси соединения к этим сервисам должны отбиваться, а не идти напрямую

**b4** — обход DPI.
- Конфиг: `/etc/b4/b4.json` (JSON, не UCI). Рядом: `geoip.dat`, `geosite.dat`, `discovery_cache.json`, `detector_history.json`, `captures/`, `b4.json.v0.bak`
- Управление сервисом: `/etc/init.d/b4 {start|stop|restart|reload}`
- **У b4 есть собственная веб-морда с API — через неё переключаются «сеты» (наборы стратегий) без рестарта.**

**happ2clash** — конвертер подписки.
- `/usr/local/bin/happ2clash` + jq-фильтр `/etc/nikki/happ2clash.jq`
- Панель провайдера самописная, ориентирована на клиент Happ, отдаёт **только Xray JSON** (массив полных конфигов), ни Clash YAML, ни base64
- Скрипт вытаскивает vless+reality+tcp узлы, подставляет имена из `remarks`, разводит дубликаты суффиксом, пишет `{proxies: [...]}` в файл провайдера и дёргает `PUT /providers/proxies/sub`
- Есть предохранитель: при нуле распарсенных узлов старый файл не перезаписывается

## 3. Что нужно выяснить самостоятельно

Эти вещи намеренно не зафиксированы — разберись по исходникам и по живой системе, затем задокументируй в README проекта.

1. **API b4.** Найди исходники (порт, эндпоинты, аутентификация, формат ответов). Нужно: получить список сетов, получить текущий сет, переключить сет. Проверь отдельно: **переживает ли выбранный сет рестарт b4** — если API меняет только состояние в памяти, демон обязан продублировать выбор в `b4.json`.
2. **Структура `b4.json`.** Правки должны быть точечными (по конкретным ключам), не перезаписью файла целиком: b4 сам мигрирует свой конфиг между версиями (`.v0.bak`), полная перезапись затрёт новые поля.
3. **Управление LED.** Проверь `trigger`/`brightness`, наличие штатных привязок в `/etc/config/system` (если светодиод уже привязан к системному триггеру, он будет драться с демоном).
4. **Имя wireless-интерфейса** в режиме station и имя сетевого интерфейса upstream (`wwan` или иное).

## 4. Архитектура

Три слоя, источник правды — UCI, а не память демона.

### Слой 1: собственный UCI-конфиг `/etc/config/netmode`

```
config main
    option mode 'nikki'          # nikki | b4 | off
    option upstream 'home'       # id активной сети

config network 'home'
    option ssid 'HomeNet'
    option encryption 'psk2'
    option key '...'
```

### Слой 2: `/usr/local/bin/netmode-apply`

Единственное место, где стартуют и останавливаются сервисы. Идемпотентный, под `flock`. Вызывается демоном, вручную из ssh и при загрузке системы.

Инвариант: одновременно активен максимум один из `nikki` / `b4`. Переключение — всегда через полный стоп обоих плюс `firewall restart`, без оптимизаций вида «b4 и так не запущен». Иначе в nftables остаются висячие цепочки.

### Слой 3: Go-демон

Отдаёт HTTP API и статику. Слушает **только на LAN-адресе**, токен в конфиге. Наружу не выставляется ни при каких условиях.

## 5. Ключевое разделение: быстрые и медленные операции

Не делать их однородными — это главное архитектурное требование.

| Операция | Механика | Время | Джоб/LED/откат |
|---|---|---|---|
| Переключить узел Nikki | Clash API | ~0.2 с | нет |
| Переключить сет b4 | API b4 | быстро | нет |
| Обновить подписку | happ2clash | 2–10 с | джоб, без отката |
| Сменить upstream WiFi | uci + `wifi reload` | 10–45 с | джоб + LED + **откат** |
| Сменить режим (nikki/b4/off) | netmode-apply | 5–15 с | джоб + LED |

Если провести быстрые операции через общий механизм джобов, получится мигающий светодиод и секундная задержка там, где должен быть мгновенный отклик.

## 6. Менеджер: сериализация и откат

```go
type Manager struct {
    mu       sync.Mutex
    job      *Job          // текущая операция, nil если простой
    rollback *time.Timer   // взведён после рискованной операции
    exec     Executor      // интерфейс — мокается в тестах
    led      LED
}
```

Правила:
- Второй одновременный джоб отбивается с `409 Busy`, а не ставится в очередь.
- Перед рискованной операцией — снапшот `/etc/config` (tar). После успеха — таймер на 90 секунд.
- Если за 90 секунд не пришёл `POST /api/confirm` — автоматический откат снапшота и возврат в прежнее состояние.

**Откат обязателен.** Сценарий: пользователь переключает upstream WiFi, будучи подключённым к роутеру через этот же канал; новая сеть не поднимается — доступа нет ни к сети, ни к панели. Без автоотката единственный выход — физический reset.

Проверить восстановление снапшота нужно **до** всего остального, включая сценарий с `reboot` в середине применения.

## 7. HTTP API

```
GET  /api/status              режим, текущий джоб, upstream, узел Nikki, сет b4,
                              время и результат последнего обновления подписки
POST /api/mode                {"mode":"nikki|b4|off"}     → job
POST /api/upstream            {"network":"home"}          → job
POST /api/confirm             {"job":"..."}
GET  /api/wifi/scan           список сетей (ubus iwinfo scan) с уровнем сигнала
GET  /api/wifi/networks       сохранённые сети из netmode
POST /api/wifi/networks       добавить/изменить сохранённую сеть
GET  /api/nikki/proxies       узлы с задержками и текущий выбранный
POST /api/nikki/proxy         {"name":"..."}              → сразу, без джоба
POST /api/nikki/test          замерить задержки всех узлов
GET  /api/b4/sets             список сетов и текущий
POST /api/b4/set              {"set":"..."}               → сразу, без джоба
POST /api/subscription/update запустить happ2clash        → job
GET  /api/logs?n=50           лог обновлений подписки
```

`/api/status` опрашивается фронтендом раз в секунду — держи его дешёвым (кэш на 500 мс для внешних вызовов).

### Нюанс по узлам Nikki

Для ручного выбора группа `PROXY` должна быть `selector`, а не `url-test`. Но при ручном выборе мёртвого узла ломается fail-closed: группа `BYPASS` видит `PROXY` как один элемент и не отличит «выбран мёртвый» от «всё умерло». Поэтому в селекторе обязателен пункт `AUTO` (вложенный `url-test`), и он же — состояние по умолчанию. Ручной выбор трактуется как временное действие: в API предусмотри `POST /api/nikki/proxy {"name":"AUTO"}` для возврата.

## 8. Светодиоды

Два физических LED дают достаточно состояний:

| Состояние | blue:status | white:status |
|---|---|---|
| off | — | — |
| Nikki активен | ровно | — |
| b4 активен | — | ровно |
| Применяется | мигает целевой | — |
| Ошибка | оба быстро мигают 3 с, затем состояние по факту | |

Для мигания использовать штатный `trigger=timer` с `delay_on`/`delay_off` — не крутить горутину.

Быстрые операции (смена узла Nikki, смена сета b4) светодиод **не трогают**.

---

## 9. Планировщик подписок

Расписание забирается у cron внутрь демона: тогда «последнее обновление», результат и логи живут в одном месте без рассинхрона. Строку из `/etc/crontabs/root` при этом убрать.

`flock` в `happ2clash` сохранить — скрипт остаётся запускаемым вручную из ssh, пересечения быть не должно.

Лог — построчный JSON (`ts`, `nodes`, `status`, `err`) в `/etc/nikki/updates.log` с обрезкой до последних 200 строк. `/var` не подходит: tmpfs, история теряется при перезагрузке.

## 10. Тестируемость

Вся работа с системой — за интерфейсом:

```go
type Executor interface {
    UCIGet(pkg, section, option string) (string, error)
    UCISet(pkg, section, option, value string) error
    UCICommit(pkg string) error
    Service(name, action string) error
    SnapshotConfigs() (string, error)
    RestoreConfigs(path string) error
    WifiScan(device string) ([]Network, error)
    Run(cmd string, args ...string) ([]byte, error)
}
```

Клиенты Nikki и b4 — тоже интерфейсы. Цель: вся логика режимов, джобов, отката и планировщика гоняется в тестах на ноуте с моками, без роутера. Смоделировать в тестах обязательно: параллельные запросы на смену режима, срабатывание отката по таймауту, недоступность API b4/Nikki, пустой результат конвертера подписки.

---

## 11. Порядок работ

1. `Executor` + снапшот/восстановление конфигов. Проверить на живом роутере, включая `reboot` в середине.
2. `GET /api/status` — заставит написать все читающие обёртки.
3. `POST /api/nikki/proxy` — первая работающая кнопка, нулевой риск потери связи.
4. Разбор API b4, `GET /api/b4/sets` + `POST /api/b4/set`.
5. Планировщик подписок и логи.
6. Смена режима (`/api/mode`) с LED.
7. **Последним** — `/api/upstream`, только после того, как откат проверен на практике.

---

## 12. Границы

- Демон не наружу: bind на LAN, токен, никакого проброса портов.
- `/etc/nikki/run/config.yaml` не трогать никогда.
- `b4.json` — только точечные правки.
- Не хранить состояние только в памяти демона: после его перезапуска картина должна восстанавливаться из UCI и живых API.
- Режимы «прозрачный репитер» и «тетеринг» в первой версии **не делаем** — заложить место в модели, но не реализовывать.
