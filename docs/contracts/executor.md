# Контракт: `Executor`

Единственная дверь демона к системе. Всё, что демон умеет сделать с
роутером, перечислено ниже — если действия нет в интерфейсе, демон его не
совершает.

Обоснование формы — [ADR-0015](../adr/0015-executor-shape.md).
Отличия от SPEC §10 — [ADR-0018](../adr/0018-spec-superseded.md).
Коды возврата `netmode-apply` — [ADR-0020](../adr/0020-netmode-apply-exit-codes.md).
Коды возврата `netmode-wifi` — [ADR-0027](../adr/0027-netmode-wifi-exit-codes.md).
`UCIRevert` и его границы — [ADR-0028](../adr/0028-uci-revert-not-rollback.md).
Лимиты на вывод — [ADR-0022](../adr/0022-external-output-limits.md).

> Блок ниже приведён **без `ctx context.Context`** — в коде он первый аргумент
> у каждого метода. Опущен для читаемости; на состав интерфейса это не влияет.

## Интерфейс

```go
// Package executor — единственная граница между демоном и системой.
//
// Правило: через интерфейс проходят СЫРЫЕ байты. Разбор — чистые функции
// в internal/uci и internal/wireless, они тестируются на записанном выводе
// роутера (docs/recon/raw/) без моков.
package executor

// ErrNotFound возвращается UCIGet, когда опции или секции не существует.
// Отличать её от ошибки выполнения обязательно: отсутствие опции `disabled`
// означает «сеть включена» (ADR-0004), а не сбой.
var ErrNotFound = errors.New("uci: записи нет")

// ErrOutputTooLarge — команда вылила в stdout больше отведённого лимита.
// Процесс снят, вывод неполон и наверх не отдаётся: разбирать нечего
// (ADR-0022). Может прийти от ЛЮБОГО метода — см. «Лимиты на вывод».
var ErrOutputTooLarge = errors.New("вывод команды превысил лимит")

type Executor interface {
	// --- UCI: чтение ---

	// UCIShow возвращает сырой вывод `uci show <pkg>`.
	// Единственный способ перечислить секции. Разбирается uci.ParseShow.
	UCIShow(pkg string) ([]byte, error)

	// UCIGet возвращает одно значение (`uci get pkg.section.option`).
	// Если записи нет — ErrNotFound.
	UCIGet(pkg, section, option string) (string, error)

	// UCIChanges возвращает сырой вывод `uci changes <pkg>`.
	// Пустой результат = стейджинг чист. Непустой = кто-то (LuCI, ssh)
	// держит незакоммиченные правки; писать нельзя (ADR-0011).
	UCIChanges(pkg string) ([]byte, error)

	// --- UCI: запись ---

	// UCIAddNamed создаёт именованную секцию: `uci set pkg.name=sectionType`.
	// Именованную, потому что индексы наружу не выходят (ADR-0005).
	UCIAddNamed(pkg, name, sectionType string) error

	// UCISet записывает одну опцию: `uci set pkg.section.option=value`.
	UCISet(pkg, section, option, value string) error

	// UCIDelete удаляет опцию, а при option == "" — секцию целиком:
	// `uci delete pkg.section[.option]`.
	UCIDelete(pkg, section, option string) error

	// UCICommit публикует стейджинг пакета: `uci commit <pkg>`.
	// Коммитит ВСЁ, что в стейджинге, включая чужое, — поэтому вызову
	// обязана предшествовать проверка UCIChanges (ADR-0011).
	UCICommit(pkg string) error

	// UCIRevert отменяет НАШ собственный черновик секции:
	// `uci revert <pkg>.<section>`. section обязателен, пустым не бывает —
	// revert по пакету снёс бы и чужое.
	//
	// Область применения — часть контракта, а не рекомендация (ADR-0028):
	//   1) только на пути ОТКАЗА записи, не при старте, не в фоне, не
	//      «заодно» при другой операции, не в обработчике чтения;
	//   2) только ДО UCICommit — после коммита это был бы возврат
	//      опубликованного состояния, то есть откат (ADR-0006);
	//   3) только по адресу секции, которую записывал этот же запрос: имя
	//      либо сгенерировано нами (создание), либо получено от target();
	//   4) собственный отказ UCIRevert ответа клиенту НЕ меняет — клиент
	//      уже получает 500 write_failed; неудачная уборка дописывается в
	//      текст и в лог, но не превращается в другой код.
	UCIRevert(pkg, section string) error

	// --- Живая система ---

	// UbusCall выполняет `ubus call <object> <method> '<args>'` и возвращает
	// сырой JSON ответа. args == nil эквивалентен `{}`.
	// Имя объекта обязано быть процитировано в docs/recon/evidence.json —
	// проверяет scripts/check-evidence.sh.
	UbusCall(object, method string, args map[string]any) ([]byte, error)

	// --- Именованные внешние действия ---

	// ApplyMode запускает /usr/local/bin/netmode-apply <mode>.
	// Единственное место старта и останова nikki/b4 (SPEC §4, Слой 2).
	// mode ∈ {"nikki","b4","off"}; проверяется до вызова.
	// Отказ возвращается ОДНИМ из исходов ниже — см. «Коды возврата
	// netmode-apply».
	ApplyMode(mode string) error

	// ApplyUpstream запускает /usr/local/bin/netmode-wifi <радио>:
	// `ubus call network reload`, затем
	// `ubus call network.wireless reconf '{"device":"<радио>"}'`, а если тот
	// отказал — запасной `/sbin/wifi reconf <радио>` (ADR-0025).
	//
	// Цель — структура, а не позиционная строка: рядом с именем радио
	// (`radio0`) в этом коде всё время ходят имя интерфейса (`phy0.0-sta0`)
	// и имя секции (`wifinet2`), и все три подходят по типу. Перепутанный
	// аргумент компилятор бы не поймал, а на роутере это `reconf`,
	// адресованный несуществующему устройству, то есть код 4 вместо
	// переключения. Поле одно намеренно: скрипту нужно ровно имя радио,
	// ВЫВЕДЕННОЕ из системы (ADR-0019), никогда не литерал.
	//
	// nil означает ровно «конфигурация передана netifd», и НИЧЕГО более:
	// код возврата глагола измеренно лжёт (ADR-0025, «мина»). Кода
	// «переключилось» у скрипта нет и не будет — вердикт выносит демон, по
	// ассоциации (ADR-0027). Отказ — ОДИН из исходов таблицы «Коды возврата
	// netmode-wifi».
	ApplyUpstream(t UpstreamTarget) error

	// UpdateSubscription запускает /usr/local/bin/happ2clash.
	// Скрипт держит собственный flock (SPEC §9) — пересечения с ручным
	// запуском из ssh безопасны.
	UpdateSubscription() ([]byte, error)

	// UCIAddList/UCIDelList — операции над UCI-СПИСКАМИ (ports у
	// bridge-vlan, network у interface relay и zone, masq_src). Появились
	// с мостом (ADR-0030): uci set списков не создаёт. del_list адресует
	// конкретное значение — снос списка целиком остаётся невыразимым.
	UCIAddList(pkg, section, option, value string) error
	UCIDelList(pkg, section, option, value string) error

	// Глаголы моста — /usr/local/bin/netmode-bridge (ADR-0030).
	//
	// BridgeStatus: `status <порт>` — JSON {relayd_installed,
	// relayd_running, carrier, speed_mbps, carrier_changes} как есть.
	// BridgeProbe: `probe <ip> <iface>` — жив ли адрес. bool, а не error:
	// «не ответил» (код 8) — факт, а не отказ, и терять различие нельзя.
	// InstallRelayd: `install` — apk add relayd, ТОЛЬКО по явному согласию
	// владельца. ApplyBridge: `apply enable|disable|access`.
	//
	// nil от ApplyBridge означает «применение выполнено», НЕ «мост
	// работает»: вердикт выносит демон по наблюдению (up у homelan с
	// нужным адресом + живой relayd) — тот же принцип, что у ApplyUpstream.
	BridgeStatus(port string) ([]byte, error)
	BridgeProbe(ip, device string) (bool, error)
	InstallRelayd() error
	ApplyBridge(action string) error

	// MissingExecutors — какие из скриптов слоя 2 не приедут в ответ на
	// нажатие: их нет на роутере или потерян бит исполнения.
	//
	// Единственный метод интерфейса, который ничего не выполняет, и это
	// осознанное исключение. Пути известны конструктору, а посмотреть на
	// них было негде: демон отдавал панель с кнопками, которые заведомо не
	// могли сработать, и узнавал об этом вместе с владельцем — после
	// uci commit, когда намерение уже опубликовано и ждёт применения.
	//
	// Возвращает ПУТИ, а не признак: «чего-то не хватает» владельцу нечего
	// делать, а «нет /usr/local/bin/netmode-wifi» он унесёт в ssh как есть.
	// Порядок фиксированный, чтобы строка в журнале и поле в /api/status не
	// переставлялись между запусками.
	MissingExecutors() []string
}
```

Девятнадцать методов. Реализация — `Exec` поверх `os/exec`; фейк — `Fake`,
чьи `Fixtures` заполняются записанным выводом из `docs/recon/raw/`.

Имена: `ApplyUpstream`, `upstreamSentinels`, `ErrUpstreamBusy`,
`ErrUpstreamApply`, `ErrUpstreamPrereq`. ADR-0027 первоначально называл их
`ApplyWireless`/`wifiSentinels`/`ErrWifi*`; расхождение сведено правкой ADR,
а не второй парой имён — контракт обязан называть то, что можно позвать.

## Почему каждый метод здесь

| Метод | Кто вызывает | Без него нельзя |
|---|---|---|
| `UCIShow` | классификация выбора, список сетей, отпечаток | перечислить `wifi-iface` — `UCIGet` адресует точечно |
| `UCIGet` | чтение `netmode.main.mode`, `network.lan.ipaddr` | читать одну опцию, отличая «нет записи» от сбоя |
| `UCIChanges` | перед каждой записью в `wireless` | заметить чужой черновик до того, как мы его опубликуем |
| `UCIAddNamed` | `POST /api/wifi/networks` (создание) | создать сеть |
| `UCISet` | создание и правка сети, запись `mode` | что-либо изменить |
| `UCIDelete` | `DELETE /api/wifi/networks/{id}`, очистка опции | удалить сеть |
| `UCICommit` | завершение записи | опубликовать изменения |
| `UCIRevert` | **только путь отказа записи**, до коммита, по своей секции | выйти из отказа, не заперев панель: брошенный черновик отбивает следующий запрос `409 foreign_staged_changes` навсегда, а недописанная секция без `disabled` ждёт чужого `uci commit` — и уезжает в живую систему включённой ([ADR-0028](../adr/0028-uci-revert-not-rollback.md)) |
| `UbusCall` | статус радио, статус `wwan`, скан, `iwinfo info` | узнать что-либо о живой системе |
| `ApplyMode` | `POST /api/mode` | сменить режим, не обходя `netmode-apply` |
| `ApplyUpstream` | `POST /api/upstream`, после `UCICommit` | применить смену upstream **узко** — так, чтобы домашняя точка не моргнула. Порядок «`network reload`, потом `reconf`» и запрет тупого `wifi` обязаны быть видны и воспроизводимы из ssh одной строкой, а не собираться заново по коду демона ([ADR-0025](../adr/0025-upstream-narrow-verb.md), [ADR-0027](../adr/0027-netmode-wifi-exit-codes.md)) |
| `UpdateSubscription` | `POST /api/subscription/update`, планировщик | обновить подписку |
| `MissingExecutors` | старт демона, сборка `/api/status` | сказать владельцу, что применять нечем, ДО нажатия. Измерено на живом роутере: демон фазы 2 приехал без `netmode-wifi`, отсутствие файла не отличалось от отказа глаголов, панель показывала «оба способа применения отказали» про механизм, который ни разу не запускался — а конфигурация к тому моменту была уже опубликована и висела неприменённой |

## Чего в интерфейсе нет — и почему

| Отсутствует | Причина |
|---|---|
| `Run(cmd, args...)` | универсальный глагол возвращает всё удалённое одной строкой: `tar` для снапшота, `/etc/init.d/b4 restart` в обход `netmode-apply`. Ни один гейт этого не поймает |
| `Service(name, action)` | сервисы стартует только `netmode-apply` (SPEC §4, Слой 2). Метод позволял бы обойти это правило, не нарушив ни одной проверки |
| `SnapshotConfigs` / `RestoreConfigs` | отката нет ([ADR-0006](../adr/0006-no-rollback.md)). Удалены, а не помечены устаревшими: удаление и есть механизм принуждения. Проверяет `scripts/check-no-rollback.sh` |
| `UCIRevert` **без ограничения области** | метод в интерфейсе появился ([ADR-0028](../adr/0028-uci-revert-not-rollback.md)), а вот полномочия «отменить что угодно» — нет. Прежняя строка («откат чужого стейджинга уничтожает чужую работу», [ADR-0011](../adr/0011-optimistic-concurrency.md)) остаётся верной ровно про **чужой** стейджинг, и именно поэтому область записана в самом контракте: только путь отказа, только до коммита, только по своей секции. Границу греп не видит — она держится тестами и ревью, и это признание, а не оговорка |
| `"network"` в `allowedUbusObjects` | `netmode-wifi` зовёт `ubus call network reload` **сам**, из шелла, где эта строка видна целиком и воспроизводима из ssh. Добавить объект в белый список демона значило бы выдать ему универсальный `network restart`/`reload` из любого места кода — вся сеть роутера одним вызовом, мимо `netmode-wifi`, мимо его `flock` и мимо запрета на грубые глаголы ([ADR-0025](../adr/0025-upstream-narrow-verb.md)). Список остаётся закрытым: `network.wireless`, `iwinfo`, `network.interface.wwan` — те же три объекта, что и до фазы 2 |
| `WifiScan(device)` | возвращал разобранные структуры — парсер оказывался за моком и переставал тестироваться. Стал `wireless.ParseScan` над `UbusCall` |
| `UCIAddAnonymous` | безымянные секции мы не создаём никогда ([ADR-0005](../adr/0005-section-name-identity.md)) |
| Работа с LED | отдельный интерфейс `led.LED`: пути в sysfs, политика best-effort, ошибки глотаются и не валят джоб. Смешивать с UCI незачем |
| Клиенты b4 и Nikki | отдельные интерфейсы поверх `net/http`. Они не системные вызовы, а сетевые |
| Чтение/запись произвольных файлов | токен читается в `cmd/netmoded` при старте обычным `os.ReadFile`; лог подписки — в `internal/logs`. Общий файловый глагол открыл бы `/etc/b4/b4.json` |

## Коды возврата `netmode-apply`

`ApplyMode` — единственный метод, у которого отказ бывает разного смысла, и
единственный, чей отказ приходит из чужого кода (шелл-скрипта). Поэтому у
него не одна ошибка, а таблица исходов.

Код возврата, а не текст: текст сообщений скрипта меняется свободно и
пишется для человека, разбирать его на стороне демона значит однажды сломать
поведение правкой формулировки. Таблица живёт в двух местах — в шапке
`files/usr/local/bin/netmode-apply` и в `applySentinels` — и меняется в них
одновременно.

| Код | Исход | Что произошло | Состояние роутера |
|---|---|---|---|
| `0` | — | режим применён | запрошенный режим работает |
| `1` | — (обычная ошибка) | некорректный аргумент или использование | не тронут |
| `3` | `ErrApplyBusy` | `flock` держит другой процесс: переключение уже идёт | **не тронут** |
| `4` | `ErrApplyFirewall` | `firewall restart` не удался дважды | оба сервиса остановлены, трафик идёт напрямую |
| `5` | `ErrApplyStart` | сервис не поднялся либо не дался его `enable` | обход не работает или не переживёт перезагрузку |
| `6` | `ErrApplyVerify` | проверка после переключения не сошлась | не то, что просили; докладывается как есть |
| `7` | `ErrApplyPrereq` | на роутере нет `flock` | не тронут |

Кода `2` в таблице нет намеренно: он традиционно занят шеллом под misuse
встроенных команд. Неизвестный код сентинелом не наделяется — «неизвестный
отказ» честнее, чем отнесённый не к тому классу.

Три правила, на которых эта таблица держится:

1. **Сентинелы добавляются, форма интерфейса не меняется.** Сигнатура
   `ApplyMode` прежняя — [ADR-0015](../adr/0015-executor-shape.md) про форму,
   а не про типы ошибок.
2. **Различение не даёт права чинить.** Демон по коду выбирает, что сказать
   владельцу и что показать светодиодом, и не пытается привести систему в
   порядок сам ([ADR-0010](../adr/0010-never-auto-repair.md)). Единственный
   повтор — вторая попытка `firewall restart` внутри скрипта; это не откат
   ([ADR-0006](../adr/0006-no-rollback.md)): состояние никуда не
   возвращается, повторяется та же операция.
3. **Аварийные сообщения скрипта идут в stderr.** Реализация собирает stdout
   и stderr в отдельные ограниченные буферы (см. «Лимиты на вывод»): stdout
   попадает в результат, а в текст ошибки — только stderr. Обычные шаги
   скрипт по-прежнему пишет в stdout, и всё дублируется в syslog через
   `logger` (диагностика по ssh — `logread`).

Отказ `4` останавливает переключение **до старта целевого сервиса**.
Поднимать туннель поверх цепочек, оставшихся в nftables от прошлого режима,
нельзя: панель показывала бы работающий режим, а трафик шёл бы мимо него.
Проверять остаточные цепочки через `nft list ruleset` скрипт не пытается —
имена цепочек nikki и b4 разведкой не подтверждены, а выдуманное имя есть
ровно та галлюцинированная интеграция, против которой стоит
`scripts/check-evidence.sh`.

Поведение скрипта проверяется запуском на подставных `/etc/init.d/*` —
`scripts/check-netmode-apply.sh` в `make checks`. Фейк `Fake` умеет отдавать
заданный код через `ApplyExitCodes[mode]` и прогоняет его через ту же
таблицу, что и реальная реализация.

## Коды возврата `netmode-wifi`

Вторая таблица исходов, у `ApplyUpstream`, и устроена она по образцу первой —
[ADR-0027](../adr/0027-netmode-wifi-exit-codes.md). Отдельный скрипт, а не
`ubus` прямо из Go, по той же причине, что и `netmode-apply` (SPEC §4,
слой 2): последовательность глаголов, их порядок и замок обязаны быть видны и
воспроизводимы из ssh одной строкой.

| Код | Сентинел | Что произошло | Состояние роутера |
|---|---|---|---|
| `0` | — | **применение выполнено**: один из глаголов принят и вернул `0` | конфигурация передана netifd; что вышло — **неизвестно скрипту** |
| `1` | — (ошибка как есть) | некорректный аргумент или использование — баг вызывающего | не тронут |
| `3` | `ErrUpstreamBusy` | `flock` держит другой процесс | **не тронут** |
| `4` | `ErrUpstreamApply` | **оба** глагола отказали | конфигурация не применялась; записанное ждёт чужого применения |
| `7` | `ErrUpstreamPrereq` | нет предусловия: отсутствует `flock` или `ubus` | не тронут |

Таблица живёт в **пяти** местах и меняется во всех сразу:

| Место | Что там |
|---|---|
| `files/usr/local/bin/netmode-wifi` | шапка скрипта |
| `internal/executor/executor.go` | `upstreamSentinels` |
| `docs/contracts/executor.md` | этот файл |
| [`docs/adr/0027-netmode-wifi-exit-codes.md`](../adr/0027-netmode-wifi-exit-codes.md) | таблица решения |
| `scripts/check-netmode-wifi.sh` | сценарии `S1`–`S13` |

Копия здесь — не дублирование ради полноты: она единственная видна тому, кто
читает документацию, не открывая ни скрипт, ни Go.

**Механического сторожа у этих пяти мест нет — и это надо прочитать
буквально.** У соседней таблицы, таксономии причин провала переключения, он
есть: `scripts/check-fail-reasons.sh` сверяет пять её источников (Go, OpenAPI,
обе локали `i18n.js`, `app.js`, мок) и валит `make verify`. У таблицы **кодов
возврата** такого гварда не существует. `check-netmode-wifi.sh` проверяет коды
живым **запуском** скрипта — то есть стережёт пару «скрипт ↔ сценарии», но не
читает ни этот файл, ни ADR, ни Go. Не переносите доверие с одной таблицы на
другую: гвард стережёт причины, а не коды.

**Кода «переключилось» в таблице нет** — и это главное её свойство.
Формулировка `0` выбрана так, чтобы её нельзя было прочитать как успех
переключения: скрипт печатает «применение выполнено», а не «сеть
переключена». Материала для вердикта у него нет — он видит только код
глагола, а тот измеренно лжёт (ADR-0025). Вердикт выносится в одном месте:
демон читает живую систему и сравнивает `associated_ssid` с запрошенным
([ADR-0002](../adr/0002-source-of-truth.md)). Второй судья в скрипте дал бы
два ответа на один вопрос, и разойдясь — панель показывает одно, `logread`
другое.

## Коды возврата `netmode-bridge`

Третья таблица исходов, у глаголов моста, по образцу двух предыдущих —
[ADR-0030](../adr/0030-bridge-layer2-teardown.md).

| Код | Сентинел | Что произошло | Состояние роутера |
|---|---|---|---|
| `0` | — | выполнено; для `probe` — адрес **ответил** | для `apply`: конфигурация передана; что вышло — **неизвестно скрипту** |
| `1` | — (ошибка как есть) | некорректный аргумент — баг вызывающего | не тронут |
| `3` | `ErrBridgeBusy` | `flock` держит другой процесс | **не тронут** |
| `4` | `ErrBridgeApply` | `network reload` или `firewall reload` отказал | закоммиченное ждёт чужого применения |
| `5` | `ErrBridgeService` | relayd не остановился после `disable` | мост может работать поверх удалённой конфигурации |
| `7` | `ErrBridgePrereq` | нет предусловия: `flock`/`ubus`/`apk`/`ping`/порт | не тронут |
| `8` | — (`BridgeProbe` → `false`) | `probe`: адрес **не ответил** — факт, а не отказ | не тронут |
| `9` | `ErrRelaydInstall` | `apk add relayd` отказал; причина в тексте | конфигурация не тронута |

Код `8` в `bridgeSentinels` не входит намеренно: его разбирает `BridgeProbe`
и возвращает `false`, а не ошибку. «Адрес свободен» — то самое суждение, на
потере которого строился живой IP-конфликт 2026-08-31.

Пять мест таблицы: шапка `files/usr/local/bin/netmode-bridge`,
`bridgeSentinels` в `internal/executor/executor.go`, этот файл,
[ADR-0030](../adr/0030-bridge-layer2-teardown.md),
`scripts/check-netmode-bridge.sh`. Механического сторожа у пяти мест нет —
та же оговорка, что у таблицы `netmode-wifi` выше, дословно.

**Пропущен `2`** — по тому же доводу, что и в
[ADR-0020](../adr/0020-netmode-apply-exit-codes.md): он традиционно занят
шеллом под misuse встроенных команд, и, навесив на него смысл, мы однажды
приняли бы опечатку в скрипте за осмысленный отказ.

**Пропущены `5` и `6`.** Совпадение с `netmode-apply` намеренное там, где
смысл совпадает: `1`, `3` и `7` означают в обоих скриптах одно и то же, и
человек, читающий `logread`, не обязан помнить, какой скрипт что означает под
тем же числом. Там, где смысла нет, число не переиспользуется: `5` — «сервис
не перешёл в нужное состояние», а `netmode-wifi` сервисов не трогает вовсе;
`6` — «верификация не сошлась», а верификации в нём нет и не будет. Дырка в
нумерации честнее числа, означающего в двух соседних контрактах разное.

**Замок отдельный — `/var/lock/netmode-wifi.lock`, не общий с
`netmode-apply`.** Операции не делят ресурс: одна останавливает и запускает
сервисы и перезапускает firewall, вторая просит netifd перечитать `wireless`.
Общий замок сделал бы «занято» ложью — владелец, меняющий режим, получал бы
код `3` на переключение сети без всякой причины. Сериализацию наших
собственных операций даёт не замок, а менеджер джобов (`409 job_busy`,
[ADR-0013](../adr/0013-fast-vs-slow.md)); замок в скрипте защищает от второго
процесса **вне** демона — ssh, cron, применение при загрузке. Цена названа
честно: `netmode-apply` и `netmode-wifi` теперь могут идти одновременно, если
один запущен демоном, а другой руками; что происходит при наложении
`firewall restart` на `network reload`, **не измерено**.

Поведение скрипта проверяется **запуском**, а не чтением:
`scripts/check-netmode-wifi.sh` в `make checks` гоняет копию
`files/usr/local/bin/netmode-wifi` с подставными `ubus`, `wifi` и `flock`.
Сценарии помечены `S1`–`S13`, и сам скрипт по завершении докладывает состав
дословно: «синтаксис, 12 сценариев поведения и самотест правил (текст +
журнал)». Среди них греп «`wifi` без `reconf` не встречается» (тупой глагол
запрещён навсегда, `S10`), греп «слова об успешном переключении в сообщении
нет» (скрипт не заявляет исхода, `S1`) и мутационный самотест `S12` —
доказательство, что правило `S10` умеет краснеть. Фейк `Fake` отдаёт заданный
код и прогоняет его через ту же таблицу, что и `Exec`.

## Исход без кода возврата: `ErrNoExecutor`

Обе таблицы выше начинаются с допущения, что скрипт **запустился**. Когда его
на роутере нет или потерян бит исполнения, кода возврата не существует вовсе,
и разбирать нечего: `os/exec` отдаёт `*fs.PathError`, а не `*exec.ExitError`.

```
| Условие                                    | Сентинел       | Состояние роутера |
| файла нет / не исполняем (fs.ErrNotExist,  | ErrNoExecutor  | не тронут         |
|   fs.ErrPermission)                        |                |                   |
```

Сентинел ОДИН на оба скрипта: различает их путь в тексте ошибки, а решение
вызывающего от того, какой именно не приехал, не зависит — оба чинятся одной
установкой пакета.

Своё имя нужно потому, что это единственный исход, у которого нет кода и при
этом есть полная определённость. Три соседних случая путались с ним ровно до
его появления:

- `ErrUpstreamApply` (`4`) — глаголы звали, оба отказали. Здесь их не звал
  никто;
- `ErrUpstreamPrereq` (`7`) — о нехватке `flock`/`ubus` докладывает сам
  скрипт; чтобы вернуть семёрку, надо сначала запуститься;
- `ErrUpstreamUnknown` (`-1`) — процесс сняли сигналом, и он мог успеть всё.
  Незапущенный не успел ничего.

Цена путаницы измерена на живом роутере: демон фазы 2 приехал без
`netmode-wifi`, отсутствие файла уходило в `default` ветку `applyReason`, и
панель показывала «оба способа применения отказали» — уверенный диагноз про
механизм, который ни разу не запускался. Владелец при этом оставался с
**опубликованной, но не применённой** конфигурацией: `uci commit` прошёл,
применить его было нечем, станция висела не подключённой до тех пор, пока он
не передёрнул радио руками.

Проверка стоит в `classifyByExitCode` **перед** разбором кода, то есть
одинаково закрывает `ApplyMode` и `ApplyUpstream`. Права чинить это демон не
получает ([ADR-0010](../adr/0010-never-auto-repair.md)) — только право
назвать: у переключения сети исход доезжает до владельца причиной
`executor_missing`, у смены режима — текстом ошибки джоба.

Отдельно от исхода стоит `MissingExecutors`: он отвечает на тот же вопрос
**до** нажатия, а не после.

## Лимиты на вывод

Дедлайн ограничивает **время** внешней команды, но не **память**: без лимита
таймаут лишь задаёт, сколько секунд у команды есть на то, чтобы съесть
роутер. У роутера порядка 512 МБ ОЗУ и нет свопа — OOM-killer убивает демон
целиком, и владелец теряет управление роутером без единой записи о причине.
Из четырёх команд (`uci`, `ubus`, `netmode-apply`, `happ2clash`) опаснее
всего последняя: 120 секунд дедлайна и чужой код внутри.

| Поток | Лимит | Что при достижении |
|---|---|---|
| stdout | 1 МиБ (`MaxStdout`) | процесс снимается, вызов возвращает `ErrOutputTooLarge`, **вывод наверх не отдаётся** |
| stderr | 64 КиБ (`MaxStderr`) | текст ошибки помечается `[…stderr усечён на 65536 Б]`, код возврата разбирается как обычно |

1 МиБ — то же число, что у буфера сканера в `internal/logs`. Запас против
самого объёмного легитимного вывода стократный: снятый `iwinfo scan` на
14 сетей — 8 989 байт (`raw/23-ubus-iwinfo-scan.json`, ~640 байт на сеть),
`network.wireless status` — 1 435 байт, `uci show wireless` — 1 583 байта.
Проверяется тестом `TestLimitCoversRealRouterOutput` — на снятых фикстурах,
а не на догадке.

**Усечение обязано быть видимым.** Молча обрезанный stdout — это огрызок
JSON, который даёт загадочную ошибку парсера: владелец ищет проблему
в нашем разборе вместо болтливой команды. Поэтому переполнение stdout —
отдельный класс отказа (`ErrOutputTooLarge`), а не тихая обрезка; байты при
нём не отдаются вовсе, разбирать нечего. Переполнение stderr отказом **не**
считается: stdout при нём полон и пригоден, а выбрасывать годные данные
из-за болтливости в другой поток значит отказывать там, где не за что.

Раньше вызовы шли через `cmd.Output()`. Он ограничивал только stderr
(~64 КиБ в `ExitError.Stderr`) — дырой был именно stdout. Отсюда ловушка при
переходе на собственные буферы: `ExitError.Stderr` становится пустым
навсегда, и текст ошибки молча пустеет, при том что `errors.Is` по коду
возврата продолжает проходить. Диагностика `netmode-apply` (`die_code` →
`err()` → stderr) держится именно на этом тексте, поэтому цепочка проверяется
отдельным тестом `TestRunStderrReachesErrorText`, а не косвенно.

>
> Имя устройства в этих вызовах подставляется то, что вернул

## Правила вызова

1. **Ни имя интерфейса, ни имя радио не хардкодятся.** `phy0.0-sta0` берётся
   из `network.wireless status` → `<radio>.interfaces[].ifname`, где в том же
   объекте лежит `section`. Связь секция↔интерфейс дана напрямую
   (`raw/21-ubus-network-wireless-status.json`). Какое радио станционное —
   выводится из `interfaces[].config.mode == "sta"`, при выключенном радио —
   из секции `wifi-iface` с `mode=sta` в UCI; не вывелось — `503
   radio_unknown` ([ADR-0019](../adr/0019-radio-role-derived.md)). Оба класса
   литералов стережёт `scripts/check-no-hardcoded-if.sh`.
2. **Запись в `wireless` идёт одной последовательностью без внешних вызовов
   между шагами:** `UCIChanges` (пусто) → `UCIAddNamed`/`UCISet`/`UCIDelete` →
   `UCICommit` → `UCIShow` (новый отпечаток). На пути отказа **до** `UCICommit`
   добавляется `UCIRevert` по своей секции
   ([ADR-0028](../adr/0028-uci-revert-not-rollback.md)); на пути переключения
   после `UCICommit` — `ApplyUpstream`.
3. **`disabled` записывается ровно в двух местах** — при создании секции, со
   значением `"1"`, и на пути переключения upstream, литералами `"0"` и `"1"`
   ([ADR-0026](../adr/0026-switch-from-ambiguous.md)). Только литералами: не
   `strconv.FormatBool`, не `fmt.Sprintf`, не вычисленная выше переменная —
   значение этой опции есть решение, а не данные, и вычисленное нельзя
   прочитать в месте записи. **`UCIDelete` с аргументом `"disabled"` запрещён
   всегда**, включая путь переключения: отсутствие опции означает «включено»
   ([ADR-0004](../adr/0004-selection-derived.md)), то есть удаление — это
   включение сети способом, который в диффе не выглядит как включение.
4. **Имя секции в записи в `wireless` никогда не строковый литерал** — адрес
   происходит из разбора `uci show` ([ADR-0005](../adr/0005-section-name-identity.md))
   либо из генератора имён при создании. Секции не станционного радио и не
   `mode=sta` не адресуются вовсе, в том числе на шаге «погасить все прочие
   включённые»: это единственная защита `radio1`/`grenderNet` и `wifi-device`
   ([ADR-0026](../adr/0026-switch-from-ambiguous.md)).
5. **Значение `key` не попадает в логи и в тексты ошибок**
   ([ADR-0012](../adr/0012-write-only-credentials.md)). Ошибка `UCISet` для
   опции `key` логируется без значения.
6. **Таймауты.** Все вызовы через `context.Context` с дедлайном: UCI и `ubus`
   status — 3 с, `iwinfo scan` — 15 с, `ApplyMode` — 60 с,
   `ApplyUpstream` — **15 с (`UpstreamApplyTimeout`)**,
   `UpdateSubscription` — 120 с. Превышение = ошибка, а не зависший
   обработчик.

   15 с у `ApplyUpstream` — это дедлайн **применения**, а не ожидания
   ассоциации, и путать их нельзя. Сам глагол измерен в 0.01–0.04 с
   ([ADR-0025](../adr/0025-upstream-narrow-verb.md)), запас трёхсотный; ждать
   ассоциацию скрипт не имеет права — он держал бы `flock` всё это время и
   закрыл бы применение для всех остальных ради информации, которую демон всё
   равно перепроверит ([ADR-0027](../adr/0027-netmode-wifi-exit-codes.md)).
   Ожидание ассоциации и IPv4 живёт в Go, после возврата `ApplyUpstream`, и
   его исход — не ошибка скрипта.
7. **Лимиты на вывод.** stdout — 1 МиБ, stderr — 64 КиБ (см. «Лимиты на
   вывод»). Превышение stdout = `ErrOutputTooLarge` и снятый процесс, а не
   молча обрезанные байты.

## Что обязано быть проверено в тестах

Список из SPEC §10, уточнённый принятыми решениями:

| Сценарий | Как проверяется |
|---|---|
| Параллельные запросы на смену режима | второй получает `409 job_busy`, первый доводится до конца |
| Недоступность API b4 | `/api/b4/*` → `503`, `/api/status` отдаёт `b4.available: false` и **не падает** |
| Недоступность Clash API | то же для `/api/nikki/*` |
| Пустой результат конвертера подписки | джоб `failed`, файл провайдера не перезаписан, строка в логе со `status: "fail"` |
| Все четыре состояния `Selection` | четыре фикстуры `uci show wireless` |
| `409` на правку включённой сети | фикстура `Single` + `POST` по её `id` |
| `409` при несовпадении отпечатка | подменить фикстуру между чтением и записью |
| `409` при чужом стейджинге | непустой вывод `UCIChanges` |
| Экранирование спецсимволов в `key` | `raw/10-uci-show-wireless.txt:41` |
| Отсутствие отката | `scripts/check-no-rollback.sh` в `make checks` |
| Каждый код возврата `netmode-apply` | подставной скрипт с нужным `exit`; проверяется исход и то, что stderr дошёл до текста ошибки |
| Команда льёт больше лимита | подставной скрипт на ~2 МиБ в stdout: `ErrOutputTooLarge`, пустой результат, снятие процесса задолго до дедлайна |
| stderr долетает до текста ошибки | подставной скрипт с текстом в stderr и ненулевым кодом — защита от пустого `ExitError.Stderr` после отказа от `cmd.Output()` |
| Лимит покрывает реальный вывод роутера | `MaxStdout` против размера самой большой фикстуры в `docs/recon/raw/` |
| Исходы различимы в `applyMode` | фейк с `ApplyExitCodes`; «занято» не мигает ошибкой, остальные мигают |
| `firewall restart` не удался | `check-netmode-apply.sh`, сценарий S2: код `4` **и** целевой сервис не стартовал |
| Каждый код возврата `netmode-wifi` | подставной скрипт с нужным `exit`; проверяется сентинел и то, что stderr дошёл до текста ошибки |
| `ApplyUpstream` не заявляет успеха | `check-netmode-wifi.sh`, сценарий S8: слов об успешном переключении в сообщении скрипта нет |
| Тупой `wifi` запрещён | `check-netmode-wifi.sh`, сценарий S7: `wifi` без `reconf` в скрипте не встречается ([ADR-0025](../adr/0025-upstream-narrow-verb.md)) |
| Отказ `UCISet` в середине создания | стейджинг после ответа **пуст**: `UCIRevert` вызван по своей секции, следующий `POST` не упирается в `409 foreign_staged_changes` ([ADR-0028](../adr/0028-uci-revert-not-rollback.md)) |
| `UCIRevert` не зовётся вне пути отказа | ни при старте, ни в фоне, ни после `UCICommit` — на фейке считаются вызовы |
| Переключение гасит только станционные секции | после `POST /api/upstream` включена ровно одна секция; `radio1` и `wifi-device` не адресованы ни одной командой |
