# Свои выходы через узлы подписки: цепочки `dialer-proxy`

**Снято 2026-11-14 на тестовой VM** (ADR-0045; nikki v1.26.1, mihomo 1.19.27)
и локально на Xray 26.10.21 (macOS, тот же релиз, что на выходных нодах).
Повод: прямой вход на свою ноду (`kz-nqz-exit-01`, VLESS + Reality +
`xtls-rprx-vision`, выходы `resi` и `dc`) могут закрыть, и тогда до неё
нужно ходить через платный узел подписки. Ответы здесь нужны для решения
о `exits.yaml`, пуле `HOP` и подписке для Happ.

Узлы подписки в VM скопированы с живого роутера (`sub.yaml` от 14.11, 38
узлов): из сети стенда подписка не скачивается (ниже). Адрес ноды и IP VPS
здесь замаскированы.

## Стенд

В профиль VM добавлены:

- `kz-nqz-exit-01-{resi,dc}` — узлы из `exports/<нода>.mihomo.yaml` как есть;
- `kz-nqz-exit-01-{resi,dc}-via-hop` — их копии с `dialer-proxy: HOP`;
- провайдер `sub-hop` (тот же `sub.yaml`) и группа `HOP` — **`select`** на
  время спайка, чтобы закреплять хопы разных типов по очереди;
- `EXIT-RESI`/`EXIT-DC` — `select [прямо, via-hop, REJECT]`;
- листенеры `mixed` на `127.0.0.1:7891/7892/7893` с `proxy: EXIT-RESI /
  EXIT-DC / HOP` — запросы через группу мимо правил. Листенеры требуют
  общую авторизацию nikki (`nikki.@authentication[0]`), `skip-auth-prefixes`
  в собранном конфиге нет.

**Ловушка yq.** `map(.["dialer-proxy"] = "HOP")` в yq, который стоит на
OpenWrt, поле **молча не пишет** — копии выходят без `dialer-proxy`, то есть
«через хоп» на деле прямые. Работает `."dialer-proxy" = "HOP"`. Проверять
поле в `run/config.yaml` после склейки, а не верить выводу команды.

## Что вышло

### Цепочка работает, vision через `dialer-proxy` не ломается

| HOP (тип) | хоп сам | `dc` через хоп | 10 МБ через `dc` |
|---|---|---|---|
| 🇩🇪⚡Германия (vless tcp reality vision) | 204, 0,3 с | IP VPS, AS41798 KZ | 22,7 с (~3,5 Мбит/с) |
| 🇷🇺💳Россия (hysteria2) | 204, 0,2 с | IP VPS, AS41798 KZ | 3,9 с (~20 Мбит/с) |
| 🇮🇹Италия SS (ss) | 204, 0,2 с | `REALITY authentication failed` | — |
| 🇨🇭⚪Швейцария (БС-1) (vless ws) | 204, 0,8 с | `REALITY authentication failed` | — |
| 🇩🇪⚪Германия (БС-6) (vless xhttp) | **000** — мёртв сам | `xhttp packet-up download bad status: 400` | — |

Через vision-хоп 6 из 6 запросов прошли и через `resi`, и через `dc`. `resi`
отвечает за 6–16 с на запрос против 1 с у `dc` при одном и том же хопе —
задержку добавляет участок «VPS → ISP SOCKS5», а не цепочка. Выход `resi`
через хоп — домашний IP `*.dynamic.telecom.kz`, как и должно быть.

**Второй inbound без flow на ноде не нужен.** Риск из `CLAUDE.md` репо
выходных нод (vision внутри `dialer-proxy`) на mihomo 1.19.27 не
подтвердился ни на vision-, ни на hysteria2-хопе.

### Часть хопов подменяет адрес назначения по SNI — Reality через них не живёт

Хопы ss и ws сами работают, а цепочка через них — нет. Проверка: через хоп
TLS на **IP нашей VPS** с SNI `example.com`
(`curl -x socks5://… --resolve example.com:443:<IP VPS> https://example.com/`,
`socks5`, не `socks5h`, — адрес уходит в прокси IP-шником):

| HOP | ответ |
|---|---|
| Италия SS, Швейцария (БС-1) ws | `200`, «Example Domain» — **соединение ушло на настоящий example.com** |
| Германия vision, Россия hysteria2 | `rc=60` — ответил наш xray (чужой сертификат), адрес не тронут |

То есть сервер хопа сниффит SNI и переписывает назначение на домен (у Xray
— `sniffing.destOverride` без `routeOnly`). Для Reality это смерть: рукопожатие
уходит на настоящий сайт маскировки, клиент видит его сертификат —
`REALITY authentication failed`. Чинить на нашей стороне нечем: любой SNI
будет переписан.

**Следствие для `HOP`.** `url-test` над `sub-hop` меряет хоп, а не цепочку:
он спокойно выберет ss-хоп с лучшей задержкой, и оба выхода лягут. Здоровье
нужно мерить **через всю цепочку до ноды**, либо держать в пуле только
проверенные типы (vision, hysteria2) — второе опирается на чужую
конфигурацию серверов, которую провайдер вправе сменить.

### Прямой вход из LAN ломает sniffer домашнего роутера

Из VM прямой `kz-nqz-exit-01-*` даёт `REALITY authentication failed`, хотя
через хоп тот же конфиг работает. С Mac без всякого прокси та же проверка
(`curl --resolve example.com:443:<IP VPS> https://example.com/`) возвращает
`200 Example Domain`: подменяет **живой роутер `192.168.9.1`** — sniffer с
`overwrite_destination=1` для TLS 443, включённый 2026-09-08
([nikki-sniffer.md](nikki-sniffer.md)). VM ходит наружу через сеть Mac,
то есть через него же.

Это не про стенд, а про телефоны: **Happ на телефоне в домашнем Wi-Fi**
пойдёт к ноде через этот sniffer, и прямые записи подписки дома работать не
будут. Собственные соединения mihomo роутера (его `EXIT-*` напрямую) через
sniffer не идут — их это не касается. Нужен пропуск без подмены для адресов
своих нод (`sniffer.skip-dst-address`) — и проверка, что миксин nikki его
доносит до `run/config.yaml`.

### Xray: `dialerProxy` на балансировщик не работает

Локально, два xray: «сервер» с SOCKS-входами `hop1`, `hop2`, `exit` и
журналом доступа, «клиент» с outbound `exit` и `sockopt.dialerProxy`:

| `dialerProxy` | `xray run -test` | работа |
|---|---|---|
| `hop1` (outbound) | OK | `hop1` принял соединение до `exit`, `exit` — до example.com, `200` |
| `hops` (балансировщик над `hop1`, `hop2`, `leastPing` + observatory) | **OK** | соединение пропадает молча: ни один хоп ничего не получил, в логе клиента ошибки нет |

Статическая проверка тег не сверяет — ошибка видна только в работе. Для
Happ отсюда: запись «через хоп» — **по одной на каждый хоп** (outbound
`exit-via-<хоп>` с `dialerProxy: <хоп>`), а «Умный маршрут» держит
балансировщик **над цепочками целиком** (`resi-via-hop_i`), а не над хопами:
балансировщик как цель правила маршрутизации работает, и observatory тогда
пробует всю цепочку, что заодно отсеивает хопы с подменой SNI.

### На что может ссылаться `dialer-proxy` в mihomo 1.19.27

Нужно для схемы «узел цепочки на каждый хоп + `url-test` над цепочками»:

| Где узел цепочки | `dialer-proxy` → | Итог |
|---|---|---|
| верхний уровень профиля | группа `HOP` | работает |
| верхний уровень профиля | узел провайдера `sub` по имени | **nikki не стартует**: `proxy [...] dialer-proxy [🇩🇪⚡Германия] not found`, `netmode-apply` — код 6 |
| провайдер (файл) | соседний узел того же провайдера | старт есть, каждое соединение — `proxyName[hopx-de] not found`, отказ (не прямой выход) |
| провайдер (файл) | группа верхнего уровня `nm-hop-de` = `select`, `use: [sub]`, `filter: ^🇩🇪⚡Германия$` | **работает**: IP VPS, 1,1–2,4 с; `GET /proxies/<узел цепочки>/delay` — 1133 мс, то есть замер идёт через всю цепочку |
| провайдер (файл) | группа `nm-hop-de` удалена | nikki стартует, соединения через этот узел — отказ; остальные выходы живы |

Вывод: `dialer-proxy` разрешается только в узлы и группы **верхнего уровня**,
и для узлов верхнего уровня — при старте (фатально), для узлов провайдера —
при каждом соединении (отказ). Отсюда раскладка, при которой выключенная
склейка не роняет движок: группы-однохопники `nm-hop-*` пишет демон в
миксин (`nikki-proxy-groups` — nikki дописывает их в начало
`proxy-groups`, `/etc/init.d/nikki:186-188`), узлы цепочек — демон в файл
провайдера, профиль владельца ссылается только на провайдер
(`use: [exits]`). `filter` — регулярка, имена хопов со скобками
(`Турция (БС-3)`) надо экранировать.

`mihomo -t` ни один из сломанных вариантов не ловит — только старт движка
или живое соединение.

## Побочное

- Тестовые листенеры на 7891/7892 сначала заняли порты redir и tproxy nikki
  (`Start Redir server error: … address already in use`): прозрачный прокси
  VM часть спайка был выключен. Перенесены на 17891–17893; на результаты
  через листенеры это не влияло.

- **Подписка не скачивается из домашней сети** (Mac, VM): домен провайдера
  резолвится живым роутером в fake-IP (`198.18.1.47`), сертификат —
  самоподписанный (`ssl_verify=18`). Демон в VM отдаёт `x509: certificate is
  not valid for any names`. Кто именно на `192.168.9.1` перехватывает домен
  (nikki или b4), не выяснялось.
- **Маска адреса подписки течёт.** `GET /api/subscription` → `masked` отдаёт
  схему, хост **и путь**; у этого провайдера секрет (UUID) — в пути
  (`internal/httpapi/subscriptionurl.go:60`). Нарушает ADR-0012/0034.
- Часы VM после паузы UTM отстали на 13 ч — `ntpd -q` перед проверками TLS.
