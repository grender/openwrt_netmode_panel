# Nikki: что Clash API знает о соединениях одного устройства

**Снято с роутера 2026-09-14**, сырьё —
[`raw/91-watch-logs-connections-hosts.txt`](raw/91-watch-logs-connections-hosts.txt);
форма ответов сверена по исходникам mihomo **v1.19.27** — той же версии, что
на железе. Повод: наблюдатель трафика устройства
([ADR-0043](../adr/0043-device-traffic-watch.md)). Владелец добавляет свои
правила для новых хостов, и самое трудное — понять, какие имена просит
устройство и какие из них уходят `DIRECT` и не отвечают. До сих пор это
делалось `curl /connections` по ssh (`raw/89`, `raw/90`).

Проба только читала. Единственное действие — три исходящих `curl` с самого
роутера, чтобы в журнал попали строки `RuleSet`.

## Итог в пяти строках

1. **Пакетов OpenWrt доставлять не нужно.** Всё, что надо наблюдателю, уже
   отдаёт mihomo по петле, а имена устройств лежат в `/tmp/dhcp.leases`.
2. **`GET /logs` льётся обычным chunked-HTTP**, WebSocket не обязателен:
   строка на каждое установленное соединение и отдельная строка на каждый
   неудавшийся дозвон. Клиент на stdlib Go — `bufio.Scanner` поверх тела.
3. **`GET /connections` без апгрейда — разовый снимок**, 107 КБ на 150
   соединений. Байты, время старта, цепочка и правило есть у каждой записи.
4. **Метки страны и ASN почти всегда пусты** — и это не поломка: mihomo их
   пишет, только когда соединение дошло до правила `GEOIP` / `IP-ASN`.
5. **Строку журнала и запись снимка склеивает пара «адрес:порт источника»**:
   id соединения в журнал не попадает.

## `GET /logs?level=info`

Заголовки (`raw/91`, часть 2):

```
HTTP/1.1 200 OK
Content-Type: application/json
Transfer-Encoding: chunked
```

До первого события заголовки не приходят вовсе: `curl -si -m 2` в первой
части пробы не получил ничего. Клиенту нужен таймаут на установку
соединения, но не на ожидание первого байта. `HEAD` отвечает `405`.

Исходник — `hub/route/server.go:474-560` (`getLogs`): без заголовка
`Upgrade: websocket` ответ пишется в тело и `Flush()` после каждого события.
Параметр `level` — `debug|info|warning|error|silent`, по умолчанию `info`;
`format=structured` меняет только обёртку (`{time, level, message, fields}`),
текст тот же. **Уровень потока не зависит от `log-level` конфига**: на
роутере стоит `warning`, а `?level=info` отдаёт `info`.

Подписчику mihomo даёт канал на 1024 события и **при переполнении молча
выбрасывает** (`select … default:` в `getLogs`). Клиент, который читает
непрерывно, этого не заметит. Клиент, который застрял, потеряет события без
сигнала.

### Форма строк

Все строки соединений порождаются в `tunnel/tunnel.go:625-650` двумя
функциями. `logMetadata` зовётся **после** удачного дозвона, `logMetadataErr`
— вместо него.

| Случай | Шаблон (`tunnel.go`) | Пример из `raw/91` |
|---|---|---|
| правило с payload | `[NET] SRC --> DST match TYPE(PAYLOAD) using CHAIN` (:639) | `[TCP] 192.168.9.219:50526 --> www.youtube.com:443 match RuleSet(nm-geosite-youtube) using BYPASS[🇫🇷⚡Франция]` |
| правило без payload | `[NET] SRC --> DST match TYPE using CHAIN` (:641) | `[TCP] 192.168.9.219:50446 --> www.google.com:443 match Match using DIRECT` |
| дозвон не удался | `[NET] dial PROXY (match TYPE/PAYLOAD) SRC --> DST error: ERR` (:629) | `[TCP] dial DIRECT (match Match/) 192.168.9.219:50440 --> 194.221.250.50:80 error: dial tcp 194.221.250.50:80: i/o timeout` |
| режим global/direct, особый прокси, без правила | `… using GLOBAL`, `… using DIRECT`, `… doesn't match any rule using …` (:636-648) | не наблюдались — у nikki режим `rule` |

Детали, от которых зависит разборщик:

- `NET` — `TCP` или `UDP` в верхнем регистре. **Строк UDP за обе части
  пробы не было ни одной**; форма взята из исходника.
- `SRC` — `Metadata.SourceDetail()` (`constant/metadata.go:228`): `ip:port`,
  а при известном процессе или uid — `ip:port(proc, uid=N)`. У TProxy на
  роутере `process` и `uid` пусты всегда, но суффикс надо допускать.
- `DST` — `RemoteAddress()` = `JoinHostPort(host-или-IP, port)`: **домен,
  если он известен** (fake-ip или sniffer), иначе адрес; IPv6 в квадратных
  скобках.
- `CHAIN` — `Chain.String()` (`constant/adapters.go:75`): одно звено как
  есть, несколько — `последнее[первое]`, то есть `группа[узел]`.
- `PAYLOAD` в строке ошибки после `/` бывает пустым (`Match/`).
- Стрелка в JSON закодирована как `>` — разбирать после `json.Unmarshal`,
  не по сырому байту.
- Самая длинная строка за 20 с — 161 символ.
- Трафик самого роутера виден с адресом аплинка в роли источника
  (`192.168.0.234`), фильтр по IP устройства его отсекает.

**Что значат два вида строк.** `info` пишется после того, как TCP до цели (или
до узла туннеля) установлен: цель ответила на рукопожатие. `warning` с `dial`
значит, что рукопожатие не удалось вовсе. Отсюда два разных вердикта, и оба —
факт, а не догадка:

- **не дозвонился** — строка `dial … error`. В `raw/91` так выглядит
  `194.221.250.50` на портах 80 и 5222 у устройства `.219`, повторяясь раз в
  несколько секунд;
- **дозвонился и молчит** — строка `info` есть, а в снимке у соединения
  `upload > 0`, `download = 0` дольше нескольких секунд. Так выглядели
  Google и Fastly у ПК в `raw/89`: рукопожатие проходит, ответа на TLS нет.

Шум: за 3 секунды `level=debug` дал 17 строк, `info` — 3. Отладочный уровень
добавляет `[DNS]`, `[Process]`, `[Rule]` и в наблюдателе не нужен.

## `GET /connections`

Исходник — `hub/route/connections.go:24-29`: без `Upgrade: websocket` отдаётся
один снимок `statistic.DefaultManager.Snapshot()`; параметр `interval` имеет
смысл только у WebSocket.

Корень: `{downloadTotal, uploadTotal, connections: […], memory}`. В момент
пробы — **107 154 байта на 150 соединений** (≈ 710 байт на запись), и почти
все они от одного устройства. Демону придётся разбирать это тело целиком
каждый тик и отбирать записи по `sourceIP` сам: фильтра на стороне mihomo нет.

Запись (`raw/91`, три примера целиком):

| Поле | Что в нём на роутере |
|---|---|
| `id` | UUID, стабилен всю жизнь соединения |
| `metadata.network` | `tcp` / `udp` |
| `metadata.sourceIP`, `sourcePort` | устройство и его порт — ключ склейки с журналом |
| `metadata.host` | домен из fake-ip; пуст у 9 из 150 |
| `metadata.sniffHost` | домен из sniffer; пуст у 144 из 150 — при fake-ip он не нужен |
| `metadata.destinationIP` | **пуст у 141 из 150**: у fake-ip соединений адрес назначения не резолвился для правил |
| `metadata.remoteDestination` | реальный адрес, куда ушло соединение; **заполнен у всех 150** |
| `metadata.destinationPort` | строка, не число |
| `metadata.destinationGeoIP` | **`null` у 146 из 150**, у остальных `["us"]` и подобное |
| `metadata.destinationIPASN` | **пуст у всех 150** |
| `metadata.process`, `processPath`, `uid` | пусты / 0 у всех: TProxy процесса не знает |
| `upload`, `download` | байты с начала соединения |
| `start` | RFC 3339 с наносекундами |
| `chains` | **от узла к группе**: `["🇫🇷⚡Франция","PROXY","BYPASS"]`, у прямых `["DIRECT"]` |
| `rule`, `rulePayload` | `RuleSet` + `nm-geosite-anthropic`, `DomainSuffix` + домен, `Match` + пусто |

### Почему нет страны и ASN

`rules/common/geoip.go:59-91` дописывает `metadata.DstGeoIP` **в момент
проверки правила `GEOIP`**, `rules/common/ipasn.go:35` пишет
`metadata.DstIPASN` в момент проверки `IP-ASN`. Правила, до которого
соединение не дошло, у него нет и метки. У нас единственное geo-правило —
`GEOIP,PRIVATE,DIRECT,no-resolve` в самом конце; до него доходят только
соединения, не пойманные наборами, и с `no-resolve` он пропускает всех, у кого
нет адреса назначения, то есть все fake-ip. Отсюда 4 метки на 150 записей.

Правила `IP-ASN` нет вовсе, базы ASN у nikki нет (в `run/` лежит только
`geoip.metadb`). Чтобы ASN появился, нужны **обе** вещи: база и правило
`IP-ASN` без `no-resolve` перед `MATCH`. Второе заставит mihomo резолвить
каждый домен, дошедший до хвоста, — ровно те соединения, ради которых
наблюдатель и нужен. В этой разведке не делалось и в первой версии
наблюдателя не используется (ADR-0043, «Чего нет»).

## Устройства в LAN

| Источник | Что даёт | Замечания |
|---|---|---|
| `/tmp/dhcp.leases` | `истечение MAC IP имя client-id`, по строке на аренду | имя `*`, если клиент его не прислал (4 из 7); файл dnsmasq, tmpfs |
| `ubus call iwinfo assoclist '{"device":"phy0.1-ap0"}'` | MAC Wi-Fi-клиентов домашней точки | объект `iwinfo` уже в белом списке `Executor`; RQ-05 |
| `ip -4 neigh show dev br-lan` | IP ↔ MAC и состояние `REACHABLE/STALE/FAILED` | новый глагол `Executor`; для списка устройств не обязателен |
| `ubus call luci-rpc getHostHints` | MAC → IPv4, IPv6, имя | объекта нет в белом списке; даёт IPv6 устройства — пригодится, если наблюдать и IPv6 |
| `/connections` | какие `sourceIP` говорят прямо сейчас | ловит устройства без аренды: статика, VM за relayd |

Из семи аренд пять — Wi-Fi (MAC совпали с `assoclist`), одна — ПК `neural` в
LAN-порту (в соседях `FAILED`, то есть сейчас не подключён), и ещё одна —
`192.168.9.238`, которого нет в `assoclist` и который в соседях тоже `FAILED`:
аренда пережила устройство. Отличать кабель от Wi-Fi можно
только вычитанием: **в аренде, но не в `assoclist`** — значит, не Wi-Fi этой
точки.

Памяти на роутере 498 МБ, доступно 282 МБ.

## Что осталось неснятым

- **Поведение потока `/logs` при перезапуске nikki** — закрывается ли тело
  чистым EOF или соединение повисает. Для этого нужен перезапуск движка, в
  разведке его не было. От ответа зависит, хватит ли наблюдателю чтения до EOF
  или нужен ещё и сторож по тишине.
- **Строки UDP** — форма только по исходнику.
- **Нагрузка**: разбор 107 КБ JSON раз в секунду на Cortex-A53 не замерялся.
- **IPv6-источники**: у устройств есть ULA-адреса, но за обе пробы ни одного
  соединения с IPv6-источником в `/connections` не было.
