# Глаголы применения: чем передёрнуть станционное радио, не уронив домашнюю сеть

Разбор замера RQ-03/RQ-04/RQ-05. Сырьё — `raw/27-rq03-apply-verbs.txt`
(сводка и инвентарь), `raw/28-rq03-samples.tsv` (сэмплер), `raw/29-rq03-events.txt`
(отметки этапов и журнал пробника). Пробник — `probes/rq03-apply.sh`.

Документ написан для того, кто будет писать применение конфигурации в фазе 2 и
через год спросит «почему именно так». Все числа ниже взяты из перечисленных
трёх файлов; там, где данных нет, так и написано — «не измерено».

---

## 1. Вопрос и почему он был блокером

`radio0` (станция 2.4 ГГц, `phy0.0-sta0`) и `radio1` (домашняя точка
`grenderNet`, 5 ГГц, `phy0.1-ap0`) — **диапазоны одной `phy0`**, а не два
независимых модуля. Это было установлено раньше (см. README разведки: одинаковый
`path`, в `/sys/class/ieee80211/` только `phy0`).

Отсюда опасение, которое и было записано как блокер фазы 2:

> если домен перезагрузки неделим, то любое применение новой upstream-сети
> передёргивает `phy0` целиком — и домашняя точка `grenderNet` моргает вместе
> с внешней. То есть каждое переключение провайдера в панели отрезает от сети
> всех домашних клиентов, включая того, кто эту панель открыл.

Проектировать фазу 2 без ответа было нельзя: от него зависит не деталь, а сам
жанр операции — «применить и показать спиннер на 3 секунды» против «применить,
предупредив пользователя, что связь сейчас пропадёт у всех».

## 2. Ответ

**Домен делим.** Существует глагол, который применяет UCI только к
станционному радио и **не трогает домашнюю точку доступа**: клиент домашней
точки не переассоциировался ни разу за шесть применений подряд.

Ключевое условие, без которого глагол молча ничего не делает, — предварительный
`ubus call network reload` (раздел 5).

## 3. Стенд и метод

Из `raw/27`, раздел `== summary ==`:

| | |
|---|---|
| станция | `radio0` / `phy0.0-sta0` / секция `wifinet3`, ssid `grenderNet idhd NONONO`, сеть `wwan` |
| домашняя точка | `radio1` / `phy0.1-ap0` / секция `wifinet1`, сеть `lan` |
| целевая сеть переключения | `wifinet0`, ssid `John24` |
| владелец (кто запускал) | `192.168.9.188`, `00:E0:4A:6A:45:AD`, связь — **провод** |
| свидетель на домашней точке | `6C:40:08:98:AA:18` (`192.168.9.212`) |
| upstream-шлюз в исходной сети | `10.84.92.31` |
| `connected_time` в `assoclist` | есть |

Метод одного замера: `uci set wireless.<текущая>.disabled=1`,
`uci set wireless.<целевая>.disabled=0`, `uci commit wireless` — затем
испытуемый глагол — затем ожидание ассоциации с `John24` и живого L3 до 45 с —
затем пауза 5 с — затем возврат **тем же глаголом**. Каждый кандидат прогонялся
дважды: без предварительного `ubus call network reload` (`pre=no`) и с ним
(`pre=yes`).

Параллельно писался сэмплер `raw/28`: состояние станции, домашней точки и
интерфейса `wwan`. Заявленный шаг сэмплера — 0.25 с; **фактический шаг между
строками в `raw/28` — 0.05 с** (медиана по 3500 строкам, диапазон 0.03–0.06 с).
То есть разрешение по времени лучше заявленного, а не хуже; все Δ ниже
округлены до 0.01 с и имеют смысл с точностью примерно ±0.06 с.

### Легенда колонок `raw/28`

| Колонка | Что это |
|---|---|
| `t` | секунды из `/proc/uptime` роутера — монотонные, не зависят от NTP |
| `phase` | метка этапа: `idle`, `scan:N`, `begin/apply/settle/revert:<кандидат>:<pre>` |
| `sta_if` | интерфейс станции (`phy0.0-sta0`) |
| `assoc_ssid` | `ubus call iwinfo info` → `ssid`. **`-` = спросили, ассоциации нет. `ERR` = спросить не смогли.** Это разные вещи |
| `ap_up` | `network.wireless status` → `radio1.up` |
| `ap_clients` | число MAC в `iwinfo assoclist` домашней точки |
| `ap_macs` | сами MAC |
| `ap_conn_time` | `connected_time` клиента — секунды с момента его ассоциации. `NA` = поля нет, **не ноль** |
| `net_up`, `net_ipv4`, `net_gw`, `net_uptime` | `network.interface.wwan status`: поднят, адрес, nexthop, аптайм |

## 4. Шесть измеренных кандидатов

Таблица из `raw/27`, раздел `== кандидаты (по возрастанию грубости) ==` —

| `ubus_reconf_dev`   | no  | 0 | 0.02s | **нет** | 0 | 0.01s | да | да | NA/NA | NA/NA | `-` |
| `ubus_reconf_dev`   | yes | 0 | 0.01s | да      | 0 | 0.01s | да | да | NA/NA | NA/NA | 0 |
| `wifi_reconf_radio` | no  | 0 | 0.04s | да      | 0 | 0.03s | да | да | NA/NA | NA/NA | `-` |
| `wifi_reconf_radio` | yes | 0 | 0.04s | да      | 0 | 0.03s | да | да | NA/NA | NA/NA | 0 |
| `ubus_downup_dev`   | no  | 0 | 0.02s | **нет** | 0 | 0.02s | да | да | NA/NA | NA/NA | `-` |
| `ubus_downup_dev`   | yes | 0 | 0.01s | да      | 0 | 0.02s | да | да | NA/NA | NA/NA | 0 |

**Расшифровка колонок** — без неё сырую таблицу читать нельзя:

| Колонка | Что означает |
|---|---|
| кандидат | идентификатор глагола (что именно вызывалось — ниже) |
| `pre` | делался ли `ubus call network reload` **перед** глаголом |
| `rc_туда` | код возврата глагола при переключении на `John24` |
| длит. (первая) | сколько выполнялся сам вызов глагола «туда», с |
| `ассоц` | наступила ли ассоциация с `John24` в пределах 45 с — **это и есть «применилось или нет»** |
| `rc_обратно` | код возврата того же глагола при возврате на `grenderNet idhd NONONO` |
| длит. (вторая) | длительность вызова «обратно», с |
| `вернулась` | вернулась ли ассоциация на исходную сеть |
| `AP_клиенты_как_в_начале` | совпал ли список MAC на домашней точке с начальным |
| `потери_владелец` | потери фонового пинга до владельца, туда/обратно. **`NA` — данных нет** (раздел 10) |
| `потери_шлюз` | то же до upstream-шлюза |
| `prerc` | код возврата `ubus call network reload`; `-` — не вызывался |

Что здесь видно сразу: **колонка `rc` бесполезна** — она равна нулю во всех
двенадцати вызовах, включая два, которые не сделали ничего. Полезна колонка
`ассоц`.

### Что за чем стоит

| Идентификатор | Дословно |
|---|---|
| `ubus_reconf_dev` | `ubus call network.wireless reconf '{"device":"radio0"}'` |
| `wifi_reconf_radio` | `wifi reconf radio0` |
| `ubus_downup_dev` | `ubus call network.wireless down '{"device":"radio0"}'`, затем `ubus call network.wireless up '{"device":"radio0"}'` |

Грубые кандидаты (`wifi` целиком, `/etc/init.d/network reload`) в этом прогоне
**не мерились**: пробник останавливается, как только узкий кандидат сработал
(`raw/29`, `[418.37]`). Их поведение известно только по финальному возврату —
см. раздел 8.

## 5. Узкий глагол и запасной

### Узкий

```sh
ubus call network reload
ubus call network.wireless reconf '{"device":"radio0"}'
```

Это самый дешёвый из сработавших: сам вызов — 0.01 с, ассоциация с целевой
сетью — через 1.97 с, IPv4 — через 5.28 с (раздел 9). Домашняя точка при этом
не шелохнулась (раздел 7).

### Запасной

```sh
wifi reconf radio0
```

Работает **и без явного предварительного `network reload`** — потому что
`/sbin/wifi` зовёт его сам. Это прямо видно в `raw/27`, разделе `== inventory ==`,
в выводе `grep -n` по `/sbin/wifi`:

```
47:	[ reconf = "$1" ] && {
48:		ubus call network reload
49:		cmd=reconf
```

Строка `wifi_reconf_radio pre=no` в таблице — единственная строка с `pre=no`,
где `ассоц=да`, и объяснение ровно в этих трёх строках шелла. Цена — вызов
чуть дороже (0.04 с против 0.01 с) и зависимость от шелл-обёртки вместо
прямого ubus.

### Крайний случай

```sh
ubus call network reload
ubus call network.wireless down '{"device":"radio0"}'
ubus call network.wireless up   '{"device":"radio0"}'
```

Тоже работает и тоже не задевает домашнюю точку, но заметно медленнее
(ассоциация +4.82 с, IPv4 +8.22 с) и на время операции интерфейс станции
пропадает совсем (`assoc_ssid` уходит в `ERR`/`-`). Брать только если `reconf`
в целевой сборке отсутствует.

### Про `radio0` в командах

`radio0` здесь — **наблюдённое** имя на этом устройстве, а не константа для
кода. Роль радио выводится из `network.wireless status` по `config.mode` секций
(`evidence.json` → `ubus.radio_role_rule`), и это проверяется механически
(`scripts/check-no-hardcoded-if.sh`). В документе имя написано дословно только
потому, что документ описывает конкретный замер.

## 6. Мина: `rc=0` не значит «применилось»

**Без `ubus call network reload` netifd не перечитывает UCI.** Оба узких
глагола в этом состоянии возвращают ноль и не делают того, что от них ждут.
Провалы разные, но одинаково тихие.

### `ubus_reconf_dev` с `pre=no`: не сделал вообще ничего

`raw/29`:

```
242.44	switch	wifinet3 -> wifinet0
242.46	apply	ubus_reconf_dev pre=no rc=0 dur=0.02
```

UCI уже переключён и закоммичен, глагол вернул `rc=0` за 0.02 с. Теперь `raw/28`,
фаза `apply:ubus_reconf_dev:no` — 870 строк, окно 242.51 … 287.49 (те самые 45 с
ожидания ассоциации, которое так и не наступило):

```
242.51|apply:ubus_reconf_dev:no|phy0.0-sta0|grenderNet idhd NONONO|true|1|6C:40:08:98:AA:18|54|true|10.84.92.1|10.84.92.31|162
287.49|apply:ubus_reconf_dev:no|phy0.0-sta0|grenderNet idhd NONONO|true|1|6C:40:08:98:AA:18|99|true|10.84.92.1|10.84.92.31|207
```

`assoc_ssid` держит прежний `grenderNet idhd NONONO` **во всех 870 строках без
единого исключения**; `net_ipv4` всё это время `10.84.92.1` — адрес старой
upstream-сети; `net_uptime` монотонно растёт со 162 до 207, то есть соединение
даже не дрогнуло. Радио не передёрнулось. Ничего не произошло.

### `ubus_downup_dev` с `pre=no`: передёрнул и вернулся на старую сеть

`raw/29`:

```
346.50	switch	wifinet3 -> wifinet0
346.53	apply	ubus_downup_dev pre=no rc=0 dur=0.02
```

`raw/28`, фаза `apply:ubus_downup_dev:no` — переходы `assoc_ssid`:

| `t` | `assoc_ssid` |
|---|---|
| 346.56 | `-` (ассоциации нет) |
| 346.98 | `ERR` (интерфейс не отвечает) |
| 347.20 | `-` |
| **348.43** | **`grenderNet idhd NONONO`** |

и дальше до конца фазы (391.96) — она же. `net_ipv4` возвращается на
`10.84.92.1` к 352.47. Радио действительно опустили и подняли — но netifd поднял
**старый** конфиг, потому что нового он не читал. `rc=0`.

### Вывод для кода фазы 2

1. `ubus call network reload` перед применением — не «на всякий случай», а
   обязательная часть операции. Либо это, либо `wifi reconf`, который делает
   его сам.
2. **Код возврата глагола применения не является признаком успеха.** Успех
   определяется только последующим наблюдением: ассоциация с ожидаемым ssid и
   живой L3 на `wwan`. Ждать до наступления или до таймаута; отсутствие
   ассоциации по таймауту — это ошибка применения, а не «долго».

## 7. Как доказано, что домашняя точка не пострадала

Прямой аргумент — `ap_conn_time`, то есть поле `connected_time` из
`ubus call iwinfo assoclist '{"device":"phy0.1-ap0"}'` для единственного клиента
домашней точки `6C:40:08:98:AA:18`.

**Почему это работает.** `connected_time` — секунды с момента ассоциации
клиента с этой точкой. Если точка перезапустилась, разослала deauth или её
интерфейс пересоздали — клиент ассоциируется заново, и счётчик начинается с
нуля. Обратное тоже верно: пока счётчик растёт непрерывно, переассоциации не
было. Это надёжнее, чем смотреть на `ap_up`: `up` может успеть вернуться в
`true` между двумя выборками, а сброшенный счётчик замести под ковёр нельзя.

**Что показал `raw/28`** (по всем 3500 строкам):

| Наблюдение | Значение |
|---|---|
| первое значение `ap_conn_time` | **37** при `t = 225.88` |
| последнее числовое значение | **230** при `t = 418.86` |
| прирост счётчика | 193 с |
| прошло времени | 192.98 с |
| **случаев уменьшения `ap_conn_time`** | **0** |
| `ap_clients` | ровно `1` в каждой строке от 225.88 до 418.86 |
| `ap_macs` | `6C:40:08:98:AA:18` в каждой из них |
| `ap_up` | `true` в каждой строке до `t = 418.41` |

Счётчик рос ровно секунда в секунду и ни разу не сбросился — сквозь все шесть
применений и шесть возвратов, включая `down`+`up` станционного радио. Клиент
домашней точки не переассоциировался ни разу. `ap_clients` не падал.

Так что общий `phy0` **не означает** общий домен перезагрузки на уровне этих
глаголов: `reconf`/`down`/`up` с аргументом `device` действуют на радио, а не
на phy.

## 8. Отрицательный контроль: метод умеет замечать моргание

Это важнее самого результата. «`ap_conn_time` не сбросился» имеет ценность
только если известно, что при настоящем моргании он бы сбросился — иначе
«ничего не произошло» неотличимо от «мы не умеем смотреть».

Контроль получился сам собой. Финальный возврат конфигурации (`raw/29`,
`[418.38] финальный возврат конфигурации`) выполняет сгенерированный
`restore.sh`, который заканчивается **тупым `wifi` целиком** — на возврате
важна гарантия, а не деликатность. Вот что сэмплер увидел сразу после,
фаза `idle` (`raw/28`, дословно):

```
418.32|revert:ubus_downup_dev:yes|phy0.0-sta0|grenderNet idhd NONONO|true|1|6C:40:08:98:AA:18|230|true|10.84.92.1|10.84.92.31|0
418.41|idle|phy0.0-sta0|grenderNet idhd NONONO|false|1|6C:40:08:98:AA:18|230|true|10.84.92.1|10.84.92.31|0
418.48|idle|phy0.0-sta0|-|false|1|6C:40:08:98:AA:18|230|false|-|-|-
418.86|idle|phy0.0-sta0|ERR|false|1|6C:40:08:98:AA:18|230|false|-|-|-
418.99|idle|phy0.0-sta0|ERR|false|0|-|NA|false|-|-|-
419.24|idle|phy0.0-sta0|ERR|false|ERR|ERR|ERR|false|-|-|-
```

Читается так:

- `t = 418.41` — `ap_up` впервые за весь прогон становится **`false`**;
- `t = 418.99` — `ap_clients` падает до **`0`**, `ap_macs` — `-`,
  `ap_conn_time` — `NA` (клиента больше нет, а не «счётчик неизвестен»);
- `t = 419.24` и далее — `ERR` во всех колонках домашней точки: объект iwinfo
  для `phy0.1-ap0` временно недоступен, точка пересоздаётся;
- к концу файла (`t = 423.39`) `ap_up` снова `true`, но `ap_clients` всё ещё
  `0` — свидетель к моменту окончания прогона переассоциироваться не успел.

Всего строк с `ap_up != true` за прогон — 13, и **все** они позже 418.41.
Строк с `ap_clients != 1` — 79, и все позже 418.99.

Итог: инструмент моргание видит, и видит крупно. Значит, отсутствие моргания
в разделе 7 — это результат измерения, а не слепое пятно. Заодно это прямое
подтверждение цены грубого глагола: **`wifi` целиком роняет домашнюю точку и
выкидывает с неё клиентов.** В фазе 2 его быть не должно.

## 9. Тайминги для проектировщика

Считано по `raw/28` и `raw/29`. Точка отсчёта (`t0`) — строка `apply` в
`raw/29`, то есть **момент, когда вызов глагола вернул управление**
(предшествующий `network reload`, если он был, в Δ не входит; сами вызовы
занимают 0.01–0.04 с, так что выбор точки отсчёта на результат почти не
влияет). Дальше в `raw/28` ищется первая строка соответствующей фазы `apply:*`
с `assoc_ssid = John24` и первая строка с адресом целевой сети в `net_ipv4`.

| `wifi_reconf_radio` `pre=no` | 307.52 | 311.44 | 3.92 с | 314.46 | 6.94 с |
| `wifi_reconf_radio` `pre=yes` | 326.57 | 329.48 | 2.91 с | 332.22 | 5.65 с |
| `ubus_downup_dev` `pre=yes` | 397.19 | 402.01 | 4.82 с | 405.41 | 8.22 с |
| `ubus_reconf_dev` `pre=no` | 242.46 | — | не наступила за 45 с | — | — |
| `ubus_downup_dev` `pre=no` | 346.53 | — | не наступила (вернулся старый ssid на 348.43) | — | — |

Что из этого следует для панели:

- **Ассоциация — 2–5 с, полноценная связь — 5–9 с.** Это одно применение, одна
  целевая сеть, один прогон. Считать верхнюю границу по этой таблице нельзя:
  здесь нет ни неверного пароля, ни слабого сигнала, ни медленного DHCP.
- **Между ассоциацией и IPv4 проходит ещё 3–4 с.** «Подключились» и «работает
  интернет» — два разных события, и показывать их надо по-разному, иначе
  пользователь увидит «готово» и попадёт в дырку без адреса.
- Таймаут ожидания в пробнике был 45 с, и провалы упирались именно в него.
  Для панели разумно брать таймаут заметно больше 9 с, но не 45 —
  и различать «ещё ждём ассоциацию» и «ассоциация есть, ждём адрес».
- **Возвраты не измерялись отдельно** как тайминг: в таблице выше только
  фазы `apply:*`. Числа для `revert:*` в `raw/28` есть, но здесь не считались.

## 10. RQ-04: рвёт ли скан активную ассоциацию

**Нет, не рвёт.** Три подряд `ubus call iwinfo scan '{"device":"phy0.0-sta0"}'`
при живой ассоциации, из `raw/27`, раздел `== rq04 scan ==`:

| # | rc | длительность | сетей найдено | ssid после | `wwan uptime` | сброс |
|---|---|---|---|---|---|---|
| 1 | 0 | 2.38 с | 23 | `grenderNet idhd NONONO` | 146 → 151 | нет |
| 2 | 0 | 2.36 с | 26 | `grenderNet idhd NONONO` | 151 → 156 | нет |
| 3 | 0 | 2.42 с | 26 | `grenderNet idhd NONONO` | 156 → 162 | нет |

Ассоциация сохранилась во всех трёх случаях, `uptime` интерфейса `wwan` рос
непрерывно и ни разу не сбрасывался в ноль — а сброс `uptime` был бы признаком
переподнятия интерфейса. В `raw/28` фазы `scan:1`, `scan:2`, `scan:3` (окно
226.00 … 242.37) подтверждают это построчно: `assoc_ssid` неизменен,
`net_ipv4` = `10.84.92.1`, `net_up` = `true` во всех 181 строке.

**Числа для проектировщика:** скан занимает **2.36–2.42 с** и находил 23–26
сетей. Это блокирующая операция такого порядка — панель обязана показывать
прогресс, а не «замереть на две с половиной секунды».

Предыдущая формулировка «закрыт косвенно» (скан выполнялся, ассоциация выжила,
прямой проверки не было) заменяется прямым ответом: проверка сделана с
непрерывным наблюдением 4 колонок за состоянием станции.

## 11. RQ-05: откуда брать число клиентов домашней точки

**Из `ubus call iwinfo assoclist '{"device":"phy0.1-ap0"}'` — и поле
`connected_time` в нём есть.** Прямая цитата из `raw/27`:

```
connected_time в assoclist: да
```

и из `raw/29`, `[225.91]`:

```
клиенты домашней точки на старте: 6C:40:08:98:AA:18; поле connected_time: да
```

Практически это подтверждено 3421 строкой `raw/28` с числовым `ap_conn_time`
(из 3500; остальные 79 — `NA`/`ERR` в хвосте после `wifi`, раздел 8). Форма
разобрана: список MAC + `connected_time` на каждого.

Что даёт `connected_time` сверх количества: **признак свежей переассоциации**.
Маленькое значение у клиента сразу после применения = его только что отцепило.
Это ровно тот сигнал, которым доказан раздел 7, и он же — готовый индикатор
для панели.

Отдельно и честно: **вопрос отвечен, функция не реализована.** Поле
`ap.clients` в нашем API остаётся `null` до отдельной задачи — теперь не потому,
что источник неизвестен, а потому что чтение не написано. Разница существенная:
блокера больше нет, есть невыполненная работа.

## 12. Чего этот замер НЕ доказал

**Фоновые пинги не измерены ни в одном прогоне.** Все колонки
`потери_владелец` и `потери_шлюз` в `raw/27` равны `NA` — во всех шести
кандидатах, в обоих направлениях. То же в `raw/29`: каждая строка `ping` —
`владелец=NA свидетель=NA шлюз=NA`, включая три строки при сканах RQ-04.

`NA` здесь означает **отсутствие данных, а не отсутствие потерь**. Причина —
дефект оснастки в измерении пинга (busybox отверг форму аргументов, фоновый
пинг не дал разбираемой строки со статистикой). Дефект уже починен в пробнике,
но починка касается будущих прогонов, а не этих цифр.

Отсюда прямо:

- Утверждение **«владелец не потерял ни одного пакета» доказательств не
  имеет.** Его нельзя писать ни в changelog, ни в UI, ни в ADR.
- Утверждение **«клиент домашней точки не переассоциировался» доказано** —
  разделом 7, независимо от пингов.

Между этими двумя утверждениями есть зазор, и он реальный: точка может не
рассылать deauth, но при этом на доли секунды перестать передавать. Такое
моргание `connected_time` не увидит. Насколько оно есть — **не измерено**.

Кроме того, **не измерено**:

- поведение грубых глаголов (`wifi` целиком, `/etc/init.d/network reload`) как
  кандидатов — прогон до них не дошёл. Про `wifi` известно только то, что
  видно в разделе 8: он роняет домашнюю точку;
- время возврата (`revert:*`) как отдельный тайминг;
- поведение при неверном пароле, слабом сигнале и недоступном DHCP — все шесть
  замеров шли по счастливому пути;
- поведение при более чем одном клиенте на домашней точке: клиент был ровно
  один;
- влияние на 5 ГГц-эфир как таковой (задержки, потери у клиентов точки) —
  измерялась только ассоциация, не качество канала.

## 13. Воспроизводимость

Прогонов было два и они независимы: первый — тот, чьи артефакты лежат в
`raw/27`, `raw/28`, `raw/29`; второй — отдельный, в проводном режиме, с
`--include-blunt`. **Таблица кандидатов во втором прогоне совпала с первой до
последней строки.**

Артефакты второго прогона на диск не попали: сбор их не сохранил из-за дефекта
обёртки (уже починенного), и остались они только в терминале владельца. Поэтому
здесь и в `evidence.json` цитируются **исключительно** числа из `raw/27-29`;
второй прогон упоминается как подтверждение воспроизводимости и ни для чего
больше. Ни одно число в этом документе не взято из него.

## 14. Итог одной строкой

Домен перезагрузки делим по радио; узкий глагол —
`ubus call network reload` + `ubus call network.wireless reconf '{"device":"<радио станции>"}'`;
`rc=0` ничего не гарантирует, успех определяется наблюдением ассоциации и L3;
домашняя точка при этом не моргает — и это проверено инструментом, который
умеет моргание видеть.
