# ADR-0002: Источник правды — UCI и живая система, не память демона

## Статус
Принято — 2026-08-02

> **Сверка с кодом — 2026-08-03.** Решение в силе; ADR задним числом не
> переписывается. Но текст ниже местами описывает как существующее то, чего
> в коде нет. Расхождения правятся кодом, а не этим файлом:
>
> - **RQ-01 закрыт** (`evidence.json` → `open_questions`): Clash API проверен, порт 9090, секрет в `nikki.mixin.api_secret`. Пометка «не подтверждено» у строки про узлы Nikki устарела.
> - Ответ `network.interface.wwan status` лежит в `raw/26-ubus-network-interface-wwan.json`, а не в `raw/20-ubus-list.txt` (там список объектов ubus).

## Контекст

Роутер редактируется не только нами. LuCI, ssh и веб-морда b4 работают с теми
же файлами и теми же сервисами. Панель — не владелец конфигурации, а один из
клиентов.

SPEC §12 уже требует: «не хранить состояние только в памяти демона, после
перезапуска картина должна восстанавливаться из UCI и живых API». Это решение
доводит требование до правила, из которого нет исключений.

## Решение

Демон **не имеет собственной модели мира**. На каждый запрос он читает
источник заново:

| Что показываем | Откуда читаем | Подтверждение |
|---|---|---|
| Сохранённые сети, выбор, отпечаток | `uci show wireless` | `raw/10-uci-show-wireless.txt` |
| Имя интерфейса станции, `pending` | `ubus call network.wireless status` | `raw/21-…json` |
| Домашняя точка доступа (ssid, band) | там же, `radio1` | `raw/21-…json` |
| Состояние upstream L3 | `ubus call network.interface.wwan status` | `raw/20-ubus-list.txt` |
| Сеты b4 и их `enabled` | `GET /api/sets` | `docs/recon/b4-api.md` |
| Живость b4 | `GET /api/version` | там же |
| Узлы Nikki | Clash API | **RQ-01, не подтверждено** |
| Режим `nikki\|b4\|off` | `/etc/config/netmode` | наш файл, [ADR-0003](0003-saved-networks-in-wireless.md) |

Единственное, что демон хранит в памяти между запросами:

1. **Текущий джоб** — по определению существует только пока процесс жив.
   После рестарта джобов нет, и это правда, а не потеря данных.
2. **Кэш 500 мс** для внешних вызовов в `/api/status` (SPEC §7) — производный,
   не источник.

Всё остальное — лог обновлений (`/etc/nikki/updates.log`, SPEC §9) и режим —
лежит в файлах, переживает перезапуск и читается заново.

## Последствия

**Приобретаем**

- Правка через LuCI видна в панели в течение секунды. Расхождения «в панели
  одно, в LuCI другое» не существует как класса багов.
- Перезапуск демона — не событие. Нет прогрева, нет восстановления, нет
  миграции состояния.
- Тест на любое состояние — это подсунуть другую фикстуру `uci show`.

**Платим**

- `/api/status` при опросе 1 Гц каждую секунду делает `uci show wireless` +
  1–2 вызова `ubus` + HTTP к b4. Кэш 500 мс режет это вдвое; ниже опускаться
  нельзя без потери отзывчивости.
- Нельзя показать историю («что было час назад») — её негде взять, кроме
  лога подписки.
- Гонка между чтением и записью существует и решается отпечатком, а не
  блокировкой файла ([ADR-0011](0011-optimistic-concurrency.md)).

## Рассмотренные альтернативы

| Вариант | За | Против | Почему не он |
|---|---|---|---|
| Кэш конфигурации в памяти с инвалидацией по `inotify` | Дешёвый `/api/status` | `inotify` ловит запись файла, но не момент `uci commit`; расхождение будет редким и невоспроизводимым — худший вид бага | Экономия ~10 мс не стоит невоспроизводимого расхождения |
| Своя SQLite/JSON-база как зеркало | Можно историю, можно транзакции | Второй источник правды. Любое расхождение с UCI придётся мирить кодом, которого сейчас нет вовсе | Прямо запрещено рамками задачи и не решает ни одной нашей проблемы |
| Читать только при изменениях, отдавать последний снимок | Меньше вызовов | «Изменение» приходит извне и мы о нём не узнаём | Не работает по построению |
