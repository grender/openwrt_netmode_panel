# ADR-0017: Опрос `/api/status` раз в секунду; без WebSocket и SSE

## Статус
Принято — 2026-08-02. Сохраняет SPEC §7.

## Контекст

SPEC §7: «`/api/status` опрашивается фронтендом раз в секунду — держи его
дешёвым (кэш на 500 мс для внешних вызовов)».

Соблазн заменить это на push очевиден: панель следит за джобом, за
ассоциацией, за состоянием b4 — то есть за меняющимися величинами, и «сервер
сам скажет» звучит эффективнее. Отсюда этот ADR: без него следующий читатель
добавит SSE как «очевидное улучшение».

## Решение

Единственный механизм обновления — **`GET /api/status` раз в секунду**.
WebSocket, SSE, long-polling не используются.

Что делает эндпоинт дешёвым:

| Источник | Стоимость | Кэш |
|---|---|---|
| `uci show wireless` | процесс, ~5 мс | нет — нужен свежий отпечаток |
| `ubus network.wireless status` | процесс | **500 мс** |
| `ubus network.interface.wwan status` | процесс | **500 мс** |
| `GET /api/version` у b4 | локальный HTTP | **500 мс** |
| `GET /api/sets` у b4 | локальный HTTP | **500 мс** |
| Clash API (Nikki) | локальный HTTP | **500 мс** |
| джоб, режим, лог подписки | память / прочитанный файл | — |

Кэш общий на процесс, не на клиента: клиент один. Пропущенный из-за кэша
интервал не теряется — следующий опрос через секунду его подхватит.

Правила, вытекающие из опроса:

1. `/api/status` **никогда не блокируется** на внешнем вызове дольше своего
   таймаута. Недоступный b4 даёт `b4.available: false` в теле, а не задержку
   и не `503` всего статуса.
2. Завершённый джоб виден 30 секунд ([ADR-0013](0013-fast-vs-slow.md)) —
   иначе при опросе 1 Гц завершение можно не увидеть вовсе.
3. Поле `generated_at` в ответе позволяет панели отличить свежие данные от
   застрявших.
4. Ответ не сжимается и не кэшируется браузером: `Cache-Control: no-store`.

## Последствия

**Приобретаем**

- Сервер не хранит подключений, не рассылает, не переподключает и не помнит,
  кому что уже отправлено. Один обработчик, одна структура.
- Обрыв связи не требует лечения: следующий опрос либо пройдёт, либо нет.
- Проверяется `curl` в цикле. Тест на «панель видит завершение джоба» — это
  тест на функцию, а не на транспорт.
- Ничего не добавляется к бинарю: `net/http` уже есть, реализации WebSocket
  в stdlib нет — она пришла бы зависимостью и упёрлась в бюджет 10 МБ.

**Платим**

- 86 400 запросов в сутки при открытой вкладке. На этом железе это несколько
  процессов `ubus` в секунду — измеримая, но приемлемая нагрузка, наполовину
  срезанная кэшем.
- Задержка отклика до 1.5 с (интервал опроса + кэш). Для смены режима
  (5–15 с) незаметно; для быстрых операций неважно, потому что они отвечают
  результатом синхронно.
- Панель, оставленная открытой на ночь, продолжает опрашивать. Ставим паузу
  по `visibilitychange` на стороне фронтенда — но это его решение, не наше.

## Рассмотренные альтернативы

| Вариант | За | Против | Почему не он |
|---|---|---|---|
| SSE (`text/event-stream`) | Реализуется на stdlib; мгновенные обновления; трафика меньше | Сервер обязан помнить подписчиков и уметь переподключение; появляется второй способ узнать состояние, который надо держать согласованным с `/api/status` | Второй транспорт ради задержки, которая никого не беспокоит |
| WebSocket | Двусторонность | В stdlib нет — зависимость, а их нет и не будет; двусторонность не нужна, команды идут обычным POST | Отвергнуто рамками задачи |
| Long-polling | Мгновенно, без нового транспорта | Держит соединение и горутину на каждый ожидающий запрос; таймауты и прокси | Сложнее опроса при том же результате |
| Опрос реже (5 с) с ускорением на время джоба | Меньше нагрузки в покое | Два режима опроса вместо одного; экономия на роутере, который и так не загружен | Оптимизация без измеренной проблемы |
