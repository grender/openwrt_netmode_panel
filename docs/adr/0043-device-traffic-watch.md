# ADR-0043: Наблюдатель трафика устройства — журнал и снимки Clash API на время сессии

## Статус

**Принято 2026-09-14, реализовано.** Демон и панель написаны, `make verify`
и `make geometry` зелены, на живом роутере ещё не проверено — что именно
осталось, сказано в «Порядке работ». Первая редакция была концептом по
разговору с владельцем; места, где код с ней разошёлся, названы в
«Последствиях» поимённо, а не переписаны задним числом: цена решения видна
только рядом с тем, что его отменило. Опирается на разведку RQ-09
([`docs/recon/nikki-watch.md`](../recon/nikki-watch.md), `raw/91`). Уточняет
[ADR-0017](0017-polling-no-push.md): панель по-прежнему только опрашивает
демона, но демон на время сессии держит один поток к mihomo по петле.
Использует свои правила [ADR-0040](0040-custom-rules-in-mixin.md) без
изменения их формы и экран [ADR-0042](0042-two-screen-panel.md), добавляя к
двум экранам третий.

## Контекст

Владелец регулярно добавляет свои правила для новых хостов. Самое трудное —
не добавить правило, а понять, **какие имена** просит устройство и какие из
них уходят `DIRECT` и не отвечают. Сейчас это делается `curl /connections` по
ssh и чтением JSON глазами: так найдены DoH у Firefox (`raw/89`),
`worldsimseries.com` за чужим `MATCH` (`raw/90`) и серверы Hetzner, до которых
не доходит UDP.

Ответы владельца 2026-09-14:

- открывать режим будут поровну в двух случаях: «на устройстве что-то не
  работает» и «с кем вообще говорит новое устройство или приложение»;
- «характер трафика» — метаданные mihomo, подпись порта и ASN; DPI не нужен;
- наблюдение — явная сессия, которая гаснет сама, когда её не смотрят;
  ничего на диск;
- из строки наблюдателя сразу добавлять правило, выбирая уровень домена;
- в режиме `off` и `b4` честно говорить, что наблюдать нечего;
- источник — журнал и снимки; экран — третий, по хешу.

Разведка показала, что всё нужное mihomo уже отдаёт, а пакетов OpenWrt
доставлять не надо. Она же показала две вещи, которых в разговоре не
было. **ASN и страны почти никогда нет**. **Строка журнала не несёт id
соединения.**

## Решение

### Источник: поток `/logs` плюс снимок `/connections`, только пока идёт сессия

Демон держит **одну сессию наблюдения на процесс**, как `job.Manager`
держит одну операцию. У сессии один IPv4-адрес устройства.

Пока сессия жива, одна горутина под `safe.Do`
([ADR-0021](0021-panic-recovery-in-goroutines.md)) делает две вещи.

1. **Читает `GET /logs?level=info`** построчно. Строка вида `match … using …`
   — установленное соединение, строка `dial … error` — неудавшийся дозвон
   (формы — `nikki-watch.md`, «Форма строк»). Строки чужих источников
   отбрасываются сразу после разбора адреса.
2. **Раз в секунду берёт снимок `GET /connections`**, отбирает записи по
   `sourceIP`, по разнице с прошлым снимком считает скорость, фиксирует байты
   исчезнувших соединений.

Журнал ловит то, что снимок пропускает: соединения короче секунды и
неудавшиеся дозвоны, которых в снимке нет вовсе. Снимок даёт то, чего нет в
журнале: байты, продолжительность, «живо ли сейчас». **Склеиваются они по
паре `sourceIP:sourcePort`**: id в журнал не попадает. Порт источника
переиспользуется, поэтому склейка ищет только среди соединений, стартовавших
не раньше чем за 5 с до строки журнала.

Панель ↔ демон — **по-прежнему только опрос** раз в секунду
([ADR-0017](0017-polling-no-push.md)). Поток живёт между демоном и mihomo на
петле и существует, только пока кто-то смотрит.

### Агрегат — адресат, а не соединение

Строка экрана — **адресат**: имя из `sniffHost`, иначе `host`, иначе
`remoteDestination`, плюс `tcp`/`udp`. Одно приложение открывает десятки
соединений к одному имени, и таблица соединений читалась бы хуже, чем
сегодняшний JSON.

```
Target {
  key, name, is_ip              // имя или адрес; is_ip — правило будет cidr
  net                           // tcp | udp
  ports []int                   // до 3 разных, по частоте
  addr                          // последний remoteDestination
  geo []string                  // destinationGeoIP, если был (редко)
  rule, payload, chain          // последние: RuleSet/nm-geosite-youtube, BYPASS[узел] | DIRECT
  first, last                   // время первого и последнего события
  count, live                   // соединений всего и живых сейчас
  up, down, rate_up, rate_down  // байты за сессию и скорость по последнему тику
  dial_errors, last_error       // из строк dial … error
  verdict                       // ok | silent | unreachable
  new                           // появился после старта сессии
}
```

**Вердикт — из наблюдения, не из догадки.**

| Вердикт | Когда | Что значит |
|---|---|---|
| `unreachable` | за последние 60 с была строка `dial … error` и не было удачного соединения | рукопожатие с целью или с узлом туннеля не прошло |
| `silent` | живое соединение старше 5 с, `upload > 0`, `download = 0`, цепочка `DIRECT` | рукопожатие прошло, ответа нет — типичная блокировка по SNI |
| `ok` | остальное | — |

`unreachable` у цепочки туннеля означает мёртвый узел, а не блокировку, и
подписывается отдельно: лечится он не правилом.

### Потолки и время жизни

- **500 адресатов** на сессию, вытеснение по `last`. Порядка 250 байт на
  адресат — сессия укладывается в 200 КБ.
- **Строка журнала — 4 КиБ** (`bufio.Scanner.Buffer`), тело снимка — 4 МиБ
  (`io.LimitReader`), по правилу [ADR-0022](0022-external-output-limits.md).
  Наблюдённый максимум — 161 символ и 107 КБ.
- **TTL 60 с без опроса** `GET /api/watch`: закрыл вкладку — через минуту
  поток закрыт, память отдана. Абсолютный потолок сессии — 2 часа.
- Таймаут на установку потока — `probeTimeout`, на чтение тела таймаута нет:
  заголовки mihomo отдаёт только с первым событием, а у тихого устройства
  событий может не быть минутами.

### Перезапуск движка

Применение своих правил перезапускает nikki
([ADR-0039](0039-geosite-rulesets-mixin-file.md)), и владелец будет делать
это прямо из наблюдателя. Сессия обязана это пережить.

- **Признак перезапуска — снимок, а не поток.** Снимок, который не ответил,
  или `uploadTotal`, ставший меньше прошлого, — это перезапуск. Поток при
  этом закрывается и открывается заново с паузами 1, 2, 5 с. На EOF потока
  не полагаемся: как он ведёт себя при перезапуске, не снято (RQ-09).
- Пока движок не отвечает, у сессии `engine: restarting`, адресаты и их
  счётчики сохраняются, живые соединения обнуляются.
- Режим сменился на `off`/`b4` — `engine: off`, сессия остаётся до TTL,
  чтобы накопленное можно было дочитать.

### Список устройств

`GET /api/watch/hosts` склеивает три источника, все читаются без новых
пакетов:

1. `/tmp/dhcp.leases` — MAC, IPv4, имя (`*` → пусто). Файл читается
   напрямую, как `mixin.yaml`: это чтение, не команда.
2. `ubus call iwinfo assoclist` домашней точки — `kind: wifi`. Объект уже в
   белом списке `Executor`. Остальные аренды — `kind: wired`. MAC сравниваются
   без учёта регистра: `assoclist` пишет их прописными.
3. Снимок `/connections` — `active: true` у говорящих прямо сейчас; адреса без
   аренды (статика, VM за relayd) попадают в список без имени, `kind: unknown`.

Попутно этот же `assoclist` закрывает давнюю невыполненную работу
`status.ap.clients`, которая до сих пор `null`. Это отдельный коммит.

### API

| Маршрут | Ответ |
|---|---|
| `GET /api/watch/hosts` | `{hosts: [{ip, mac, name, kind, active}]}` |
| `POST /api/watch` `{ip}` | `200` состояние сессии. Прежняя сессия заменяется. `409 engine_off`, если режим не `nikki`. `400 bad_ip`, если адрес не из подсети LAN |
| `GET /api/watch` | `{active, ip, since, engine, unparsed, dropped, targets: [Target]}`; продлевает TTL; `Cache-Control: no-store`. Без сессии — `{active: false}` |
| `DELETE /api/watch` | `204` |

`unparsed` — строки журнала, которые разборщик не узнал. Больше нуля значит,
что mihomo сменил формат строки, и панель говорит об этом прямо; снимки при
этом работают. `dropped` — вытесненные сверх потолка адресаты.

**Нового эндпоинта записи нет.** Кнопка в строке кладёт правило в тот же
черновик своих правил, что и настройки (`RulesDraft` в `App`), и применяется
тем же `PUT /api/nikki/rulesets`. Пачка правил — один перезапуск движка.

### Панель: третий экран `#watch`

- `routeOf` получает третий экран. На полке главной появляется строка-сводка:
  «Наблюдаю neural · 12 мин · не отвечают: 2» или «Наблюдатель выключен». В
  шаге «Свои правила» появляется ссылка «подсмотреть у устройства».
- Шапка: выбор устройства (имя, адрес, значок Wi-Fi или кабеля, «говорит
  сейчас»), время с начала, состояние движка, «Стоп».
- **Два порядка одной таблицы** — под оба сценария владельца. «Проблемы
  первыми»: `unreachable`, `silent`, затем `DIRECT` по `Match`. «По трафику»:
  по байтам за сессию. Пометка «новый» держится 30 с.
- Строка: имя (для правила кликом выбирается уровень —
  `rr1---sn-5hne6n6z.googlevideo.com` → `googlevideo.com`), адрес назначения,
  подпись порта, правило → цепочка, ↑/↓ и скорость, число живых, вердикт.
  Кнопки «в туннель» и «напрямую». У голого адреса правило — `cidr` `/32`.
- Если домен уже покрыт своим правилом из черновика, вместо кнопок показано
  это правило: второе было бы недостижимо (ADR-0040, дубли).
- Внизу — полоса черновика «к применению: 3 · Применить», тот же
  `dirtyCount` и тот же джоб. После применения наблюдение продолжается, движок
  показывает «перезапускается».
- **Подпись порта** — таблица в коде панели, не в словаре: `443/tcp` — TLS,
  `443/udp` — QUIC, `53` — DNS, `853` — DoT, `5223` — APNs, `5222` — XMPP, `3478`
  — STUN, `51820/udp` — WireGuard, прочее — `номер/протокол`.
- Узкий экран: строка в две строки — имя и вердикт сверху, остальное под
  ними. `make geometry` получает состояние `watch`.
- Экран опрашивает `GET /api/watch` своим циклом только пока открыт;
  общий опрос статуса не меняется.

### Панель: решения экрана

Разметка нарисована в Claude Design («netmoded Watch.dc.html», проект
`App UI flow optimization`) и в нескольких местах ушла дальше первой
редакции этого ADR. Каждое расхождение — с доводом; вкуса тут нет.

**Пять наборов колонок вместо одной таблицы.** «Куда идёт» (вердикт ·
правило → куда · времена), «Трафик» (за сессию · сейчас · соединений),
«Сломано» (только не-`ok`), «Порты» (адрес · порт · страна), «Всё» (девять
колонок, липкое имя и своя горизонтальная прокрутка внутри карточки). У
активного устройства 50–150 строк, и два сценария владельца смотрят на
разные поля: «что сломано» — на вердикт и ошибку, «с кем говорит новое
устройство» — на трафик и правило. Одна таблица со всеми колонками не
влезает даже на 1440, а на 390 не влезает вовсе. Сегменты, а не вкладки: в
панели один идиом для «одно из N».

**Кнопок правила в строке нет ни в одном режиме.** Правило пишется в
РАСКРЫТОЙ строке, где видно, на что именно оно встанет. Первая редакция
ставила «в туннель» и «напрямую» прямо в строку — это триста кнопок в
таблице из полутора сотен строк и ни одного места, где показать выбранный
уровень домена.

**Уровень правила и маска подсети.** У домена имя разбито на части, нажатие
берёт «отсюда и правее» со всеми поддоменами; предвыбор — домен второго
уровня. У голого адреса выбирается маска `/32`, `/24` или `/16`: ADR знал
только `/32`, но сервис отвечает и с соседних адресов, а «полстраны в
туннель» пишут руками. Адрес приводится к первому в подсети — иначе демон
отобьёт правило кодом `bad_rule`, и владелец узнает об этом после
«Применить».

**Направление предвыбрано ПРОТИВОПОЛОЖНЫМ текущему.** Правило заводят,
чтобы изменить решение, а не закрепить его. Если владелец всё же выбирает
то же направление, строка под сегментом говорит об этом прямо: «сейчас
адресат и так идёт напрямую по правилу „остальной трафик“; своё правило
закрепит это решение, даже если набор изменится».

**Порядок заморожен, новые ждут в своей полосе.** Живая сортировка
«Проблемы первыми» переставляла бы строку под пальцем ровно в тот момент,
когда по ней целятся. Поэтому появившиеся при наблюдении адресаты в общий
порядок не входят, пока владелец не нажмёт «влить в список», а полоса новых
стоит ВСЕГДА, даже пустая: так таблица под ней не прыгает при появлении
строки. Смена порядка и «влить» — явные действия владельца, там переставлять
можно.

**Поиск по имени.** Второй сценарий — «разобрать список целиком» — на
полутора сотнях строк без него не работает.

**Подтверждение ухода с непримененным черновиком.** «Стоп» и «Сменить» при
непустом черновике спрашивают, и текст называет ту кнопку, которую нажали:
правила живут в этой сессии наблюдения и исчезают вместе с ней.

**У «не отвечает» через туннель кнопок нет вовсе**, а есть объяснение:
причин две — либо не отвечает узел, либо адресат закрыт именно с той
стороны, — и различить их можно по соседним строкам через тот же узел.
Правило тут не поможет ни одно.

**Страна ставится, только если она есть.** Пустая строка «страна: —»
утверждала бы, что определить не смогли, а её просто нет у 97 записей из
100.

### Сводка на полке главной едет в статусе

`GET /api/status` получает поле `watch`: адрес, начало, состояние движка и
число адресатов не в порядке. `null` — сессии нет.

Побочным запросом это было бы неверно: строка полки обязана называть
СОСТОЯНИЕ, а снимок на момент открытия главной врал бы всё остальное время —
«не отвечают: 2» осталось бы на экране после того, как всё ожило.

Условие, на котором поле туда попало, жёсткое: собирается оно `Session.State`,
который TTL **не продлевает**, в отличие от `Poll` под `GET /api/watch`.
Возьми оно `Poll`, и обещание «закрыл вкладку — через минуту погасло»
отменилось бы для всякого, кто просто ушёл с наблюдателя на главную, — то
есть для всех. Ради этого у сессии два метода, и разницу между ними стережёт
тест, а не комментарий.

Таблицы адресатов в статусе нет и не будет: он опрашивается раз в секунду, и
пятьсот строк ездили бы в нём на каждом экране, включая те, где их никто не
смотрит.

## Чего нет в первой версии

- **ASN.** Владелец его просил. Mihomo пишет ASN, только когда соединение
  проверяется правилом `IP-ASN`. Для этого нужны база ASN у nikki и такое
  правило без `no-resolve` перед `MATCH`. Тогда mihomo начнёт резолвить
  каждый домен, дошедший до хвоста, то есть ровно те соединения, ради
  которых нужен наблюдатель. Вместо ASN показывается адрес назначения:
  `remoteDestination` заполнен у всех записей. Метка страны видна там, где
  mihomo её поставил сам, это примерно 3 записи из 100.
- DNS-запросы устройства: они есть только на уровне `debug`, а он в шесть раз
  шумнее.
- История дольше сессии, запись на диск, наблюдение за всеми устройствами
  сразу, несколько сессий.
- Режимы `off` и `b4`: экран объясняет, что наблюдать нечего, и ведёт к
  карточке движка. Разбирать conntrack ради голых адресов без правил не стоит.
- IPv6-источники: у устройств есть ULA-адреса, но за пробу соединений с ними
  не было. Сессия привязана к одному IPv4.
- DPI и классификация по приложениям.

## Последствия

**Платим.**

- **Разборщик строки журнала — чужой формат без контракта.** Он привязан к
  `tunnel/tunnel.go` v1.19.27 и пинится тестами на строках из `raw/91`.
  Смена формата видна владельцу как `unparsed > 0`, а не как пустой экран.
- **Разбор 107 КБ JSON раз в секунду** на Cortex-A53, пока идёт сессия.
  Не замерено; замер — часть второй фазы, до панели.
- **Исключение из ADR-0017.** Демон держит соединение к mihomo, переподключает
  его и помнит состояние между запросами. Это ровно то, от чего 0017
  отказывался. Цену ограничивают одна сессия, петля и TTL.
- **Mihomo молча теряет события** при переполнении канала подписчика на 1024.
  Непрерывное чтение этого не допускает, зависший читатель допустит без
  сигнала.
- **Гейт `check-evidence.sh` пропустит `/connections` и `/logs`.** Пути Clash
  API он сверяет по шаблону `/proxies*|/providers/*|/version|/delay*`, этих
  путей в шаблоне нет. Шаблон расширяется тем же коммитом, что клиент.
- Вердикт `silent` — порог в 5 с. Долгий запрос без ответа, например
  long-polling, будет помечен ложно. Это подсказка, а не автоматика: правило
  добавляет человек.

**Получаем.** Цикл «посмотрел → добавил → проверил» замыкается в одном
экране, без ssh. Неудавшийся дозвон виден как факт из журнала, а не как
вывод из нулевых байт. Короткие соединения, которые `curl /connections`
глазами пропускал, в списке есть.

### Где первая редакция разошлась с кодом

Всё перечисленное написано так, как было задумано, и переделано так, как
работает. Довод каждый раз один и тот же: задумано было по чтению чужого
исходника, а сделано против него.

**`probeTimeout` на установку потока так не выражается.** Все сроки в
`internal/nikki` — это `context.WithTimeout`, а дедлайн контекста отменяет и
чтение тела: поток умирал бы через `callTimeout` на исправном роутере.
У `LogStream` свой `http.Client`, где единственный срок стоит на наборе
номера, `ResponseHeaderTimeout` нулевой, а контекст служит только каналом
отмены.

**`bufio.Scanner.Buffer` на 4 КиБ — не потолок, а убийца потока.**
`bufio.ErrTooLong` терминальна: одна длинная строка закрыла бы поток, а
повторяясь — увела бы наблюдателя в вечный цикл переподключений, который
владелец читает как «движок перезапускается». Читаем `bufio.Reader`,
длинную строку пропускаем и считаем в `unparsed`.

**Склейка, как описана, не находит ровно то, ради чего заведена.** Строка
журнала пишется в момент удачного дозвона, то есть РАНЬШЕ, чем соединение
попадёт хоть в один снимок: искать «среди стартовавших за 5 с до строки»
негде. Работающая форма — метка, которую забирает следующий снимок в том же
окне. И то, что склейка покупает, теперь названо: одно соединение, увиденное
обоими источниками, считается один раз.

**`unparsed` кричал бы волками.** При `level=info` mihomo пишет и свои
стартовые строки — после каждого перезапуска движка, который владелец
запускает с ЭТОГО ЖЕ экрана. Поэтому корзины три, а не две: разобрано /
чужое (молча отбрасывается) / не разобрано (только `[TCP]` и `[UDP]`, не
поддавшиеся грамматике).

**`new` был бы истинным у всех в нулевую секунду.** Сессия стартует пустой,
и первый снимок приносит всё, что и так шло. Новым считается только
появившийся ПОСЛЕ первого снимка, и пометка гаснет сама через 30 с — считает
её демон, потому что гаснуть она обязана и когда на экран никто не смотрит.

**У «не отвечает» через туннель не было поля для отдельной подписи.** В
`Target` лежала только последняя цепочка. Добавлено `error_chain`: искать
квадратные скобки в `chain` значило бы программировать на форме имени узла.

**Перезапуск по одному промаху пугал бы зря.** Уменьшение `uploadTotal`
доказательно и действует сразу; отказ снимка неоднозначен и ждёт второго
подряд — иначе один потерянный запрос переводил бы экран в «движок
перезагружает конфигурацию» на ровном месте.

**Сессии никто не сообщал о смене режима.** `engine: off` требует знать
режим, а у сессии нет исполнителя. Режим спрашивается замыканием и ТОЛЬКО
при отказе снимка: каждый тик — это семь тысяч запусков `uci` за двухчасовую
сессию.

**`GET /api/watch/hosts` в режимах `off`/`b4` не был описан.** Он
деградирует, а не отвечает `409`: список устройств нужен панели ровно затем,
чтобы объяснить, почему наблюдать нечего.

**Форма ответа `assoclist` не снята.** В `raw/91` команда прошла через
`grep mac`, и обёртка `{"results": […]}` выведена по отступам и по соседнему
`raw/23`. Разбор поэтому терпимый: форма не та — вид связи у всех становится
«неизвестно», а не «кабель». Снимается одной командой при следующем заходе
на роутер (RQ-05).

**Полный снимок `/connections` в `docs/recon/raw/` положить нельзя:**
107 154 × 10 больше `executor.MaxStdout`, и `TestLimitCoversRealRouterOutput`
упал бы. Объём в тестах синтезируется из двух дословных записей, а потолок
не поднимается — он держит ADR-0022 для четырёх посторонних команд.

**RQ-09 остался открытым намеренно.** Как ведёт себя тело `/logs` при
перезапуске nikki — чистым EOF или повисшим соединением — не снято, и ответ
не нужен: конец потока лечится переподключением, а повисший рвётся по
признаку из снимка. Пробовать на живом роутере ради ответа, который ни на что
не влияет, незачем; увидим сами, когда владелец применит правила из
наблюдателя.

**Цена сериализации ответа не была посчитана.** «250 байт на адресат» —
оптимизм: одно имя бывает 253 Б, и с `addr`, `rule`, `chain` и
`last_error` выходит 400–600. При пятистах адресатах это 250–300 КБ
отформатированного JSON, который `writeJSON` собирает каждую секунду на том
же процессоре, что разбирает 107 КБ снимка. Замер на железе обязан включать
ОБА числа, а не только разбор.

## Рассмотренные альтернативы

- **Только снимки `/connections`.** Один разборщик, меньше кода. Отвергнуто
  владельцем: соединения короче секунды теряются, а «не дозвонился» в
  снимке не бывает вовсе — дозвон, который не удался, соединением не стал.
- **WebSocket к `/connections?interval=…`.** Даёт те же посекундные снимки,
  что и опрос, но требует клиента WebSocket на stdlib. Выигрыша нет.
- **Панель сама ходит в Clash API.** Секрет ушёл бы в браузер вторым путём
  ([ADR-0023](0023-nikki-panel-secret-on-demand.md)), а сессия умирала бы с
  перезагрузкой вкладки.
- **Всегда наблюдать за всеми** кольцевым буфером. Поток и память на роутере
  круглые сутки ради того, что открывают раз в неделю. Владелец выбрал сессию.
- **tcpdump, conntrack, netifyd или nDPI на роутере.** Домена и правила у них
  нет, а это главное. Цена — пакеты, процессор и второй источник правды о
  соединениях рядом с mihomo.
- **Отдельный эндпоинт «добавить правило из наблюдателя».** Это был бы второй
  путь записи `mixin.yaml` мимо черновика и отпечатка. Черновик уже умеет всё
  нужное.

   (`/connections`, `/logs`, `lan_hosts`, RQ-09), этот ADR.
2. **Демон** — сделано: `nikki.Connections` и `nikki.LogStream` с потолками
   тела и строки, шаблон гейта evidence; `internal/watch` — разборщик,
   склейка, вердикты, вытеснение, TTL, переподключение; четыре маршрута

   `make verify` зелен.
3. **Панель** — сделано: `Watch.tsx`, строка полки из поля `watch` статуса,

   состояние `watch` в `make geometry` — оба зелены.
4. **Осталось, и только на железе.**
   - Замер процессора: разбор 107 КБ JSON раз в секунду ПЛЮС сборка ответа

## Чем проверяется

**Go** (`make verify`):

- `internal/nikki`: разбор двух записей снимка ДОСЛОВНО из `raw/91` — порт
  строкой, пустой `destinationIP` у fake-ip, порядок `chains`; потолок тела
  снимка; и три теста потока, из которых главный медленный намеренно —
  `TestLogStreamOutlivesCallTimeout` доказывает, что у тела сроков нет
  вовсе. Плюс пропуск слишком длинной строки без конца потока.
- `internal/watch`: разборщик на всех записанных строках `raw/91` и на
  формах из исходника, которых на роутере не случилось (UDP, суффикс
  процесса, IPv6 в скобках, пустое значение после «/», «doesn't match any
  rule», режим global); разделение «чужое» и «не разобрано»; склейка внутри
  окна и за ним; байты исчезнувшего соединения; скорость по ИЗМЕРЕННОМУ
  времени тика; таблица вердиктов строка за строкой; пометка «новый» только
  после первого снимка; вытеснение сверх 500; TTL, абсолютный потолок,
  перезапуск по отказу снимка и по уменьшению `uploadTotal`,
  переподключение потока.
- `internal/httpapi`: `409 engine_off` вне режима `nikki`, `400 bad_ip` на
  чужой подсети и на IPv6, замена сессии, `204` без тела, `Cache-Control`,
  список устройств при лежащей точке доступа и без файла аренд, остановка
  сессии вместе с демоном. И два теста про сводку в статусе: она там ЕСТЬ и
  она НЕ продлевает TTL, а `GET /api/watch` продлевает.

**Панель**: `tsc` (пропуск ключа в `en.json` роняет сборку),
`check-routes` (три источника маршрутов), `check-panel-build`,
`make geometry` — состояние `watch` на 320, 390 и 1440: горизонтальной
прокрутки нет нигде, пустых областей нет.

**На железе** — см. «Порядок работ», пункт 4.

**Чего не стережёт никто.** Что форма строки у следующей версии mihomo та
же: это видно только по `unparsed` на живом роутере после обновления nikki.
Что режим «Всё» не уносит документ вбок на узком экране: набор колонок —
состояние компонента, а не адрес, а оснастка не делает ни одного клика.
Удерживается это тем, что таблица широкого режима прокручивается внутри
своей карточки, а не растит страницу.
