# ADR-0014: Bind только на LAN, токен в сайдкаре 0600

## Статус
Принято — 2026-08-02. Уточняет SPEC §12.

## Контекст

SPEC §12: «демон не наружу: bind на LAN, токен, никакого проброса портов».
Требование верное, но недосказанное в двух местах.

Первое: **куда класть токен.** SPEC §4 подразумевал наш UCI-конфиг. Разведка
(`raw/40-etc-config-perms.txt`) показала, что `/etc/config/wireless` имеет
права `644` — то есть в этом каталоге мировидимость файла зависит от пакета,
а не от политики. Класть секрет туда, где сосед по каталогу читается всеми, —
рассчитывать на аккуратность будущих правок.

Второе: **от кого защищаемся.** В LAN один пользователь, доверенный. Реальная
угроза — не он, а **браузер**: любая открытая вкладка может отправить запрос
на `http://192.168.9.1:8080/api/mode`. Пароля браузер не знает, но
cookie-сессию отправил бы автоматически, а форму без CORS-предполёта — тем
более.

## Решение

**Bind.** Слушаем только адрес из `netmode.main.listen` (сид — `192.168.9.1`,
LAN-адрес роутера, `raw/11-uci-show-network.txt`). Если опции нет, адрес
выводится из `network.lan.ipaddr`. Если и это не удалось — **демон не
стартует**. Отката на `0.0.0.0` нет ни при каких условиях: неудачная попытка
определить LAN-адрес не должна превращаться в открытый наружу порт.

**Токен.** Файл `/etc/netmoded/token`, права `0600`, владелец `root`,
каталог `0700`. 32 случайных байта из `crypto/rand`, в base64url. Создаётся
при первом старте, если файла нет; существующий не перезаписывается никогда.
Ротация = удалить файл и перезапустить демон.

В UCI токена нет — в `/etc/config/netmode` лежит только **путь** к нему
(`option token_file`). Причины: права UCI-файлов задаёт не наша политика;
UCI-файлы попадают в бэкап sysupgrade и в редактор конфигурации LuCI; ротация
секрета не должна быть правкой конфигурации.

**Проверка запроса.** Каждый `/api/*`:

1. `Authorization: Bearer <token>`; сравнение через
   `crypto/subtle.ConstantTimeCompare`. Нет или не совпал → `401 unauthorized`.
2. Если в запросе есть заголовок `Origin` и он не равен нашему собственному
   происхождению → `403 forbidden_origin`. Заголовков CORS не отдаём никогда,
   `Access-Control-Allow-Origin` в коде отсутствует.

**Как токен попадает в панель.** Статика (`/`, `/assets/*`) отдаётся без
токена; в `index.html` при отдаче подставляется значение токена. Чужой сайт
не сможет его прочитать: межсайтовый `fetch` без CORS не даёт доступа к телу
ответа, а без токена запросы к `/api/*` отбиваются `401`. Отдельной страницы
входа нет — пользователь один и он уже за LAN.

**Чего нет:** TLS (самоподписанный сертификат в LAN даёт предупреждение
браузера и ничего не даёт по безопасности), сессий, cookie, пользователей,
ролей, ограничения частоты запросов.

> **NEEDS RECON** — свободен ли порт `8080` на этом роутере. В разведке
> `netstat` снят только с фильтром по b4 (`raw/50-b4-api.txt`), полной
> картины нет. Разрешается: `netstat -lntp`

## Последствия

**Приобретаем**

- Секрет живёт в одном файле с явными правами; его форма не зависит от того,
  как пакет решил обращаться с правами в `/etc/config`.
- Ротация — `rm` + рестарт, без правки конфигурации и без риска задеть
  соседние опции.
- CSRF из чужой вкладки закрыт двумя независимыми механизмами (токен и
  проверка `Origin`), ни один из которых не требует cookie.
- Порт наружу не откроется даже при ошибке чтения конфигурации.

**Платим**

- Токен виден в HTML-исходнике страницы панели. Это осознанно: доступ к панели
  в LAN и есть доступ к API.
- Трафик в LAN не шифрован. Кто-то в той же сети с доступом к трафику видит
  всё, включая токен и пароли, отправляемые на запись.
- Демон не запустится, если LAN-адрес поменяли, а конфиг не обновили. Отказ
  громкий и объяснимый, но это отказ.
- `curl` из ssh требует прочитать файл токена — на одну команду больше.

## Рассмотренные альтернативы

| Вариант | За | Против | Почему не он |
|---|---|---|---|
| Токен в `/etc/config/netmode` | Один файл конфигурации | Права соседних UCI-файлов разнородны (`wireless` — 644); попадает в бэкап и в редактор LuCI | Разведка прямо показала проблему |
| Без токена, только bind на LAN | Ноль трения | Любая вкладка в браузере пользователя может дёрнуть `POST /api/mode` | CSRF — реальная угроза здесь, а не гипотетическая |
| Basic-auth + пароль | Знакомо, работает в `curl` | Браузер шлёт учётные данные автоматически → CSRF возвращается; нужен UI ввода пароля | Хуже токена по обоим пунктам |
| Cookie-сессия + CSRF-токен | Классика веба | Cookie и есть источник CSRF; требует страницы входа и хранения сессий | Больше механики ради того же результата |
| TLS с самоподписанным сертификатом | Шифрование в LAN | Предупреждение браузера при каждом заходе; управление сертификатом на роутере | Цена в UX выше выигрыша для одного доверенного пользователя |
