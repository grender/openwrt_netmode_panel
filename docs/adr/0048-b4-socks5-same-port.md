# ADR-0048: Прокси для ПК на одном порту в режимах nikki и b4 — SOCKS5 b4 зеркалит mixed-port

## Статус

Принято 2026-09-25. Дополняет [ADR-0007](0007-b4-api-only.md): список
поверхностей API b4 расширен тремя вызовами (ниже). Остальное из 0007 в силе —
`b4.json` не читается и не пишется.

## Контекст

В режиме nikki на роутере есть входящий прокси — mixed-port mihomo
(`nikki.mixin.mixed_port`, по умолчанию 7890): HTTP и SOCKS5 на одном
порту, логин из `nikki.@authentication[0]`. Им пользуются ПК, которым
прозрачный туннель не подходит, и Mac со стендом (ADR-0045, ADR-0047:
`127.0.0.1:17890` → VM `7890`).

В режиме b4 `netmode-apply` останавливает nikki (одновременно работает
максимум один движок), и порт молчит — прокси для ПК пропадает вместе с
режимом. Требование владельца: **порт прокси одинаков в обоих режимах.**

У b4 есть встроенный SOCKS5-сервер (`system.socks5`, по умолчанию выключен,
порт 1080; `src/config/config.go:232-238`). Его исходящие соединения — обычный
`net.Dial` с роутера без метки (`src/socks5/server.go:331`), они проходят
цепочку `output` таблицы `inet b4_mangle` (`src/tables/nftables.go:278-290`)
и обходят DPI так же, как трафик LAN.

## Решение

**В режиме b4 SOCKS5 b4 слушает порт mixed-port nikki с логином nikki.**
Клиентам нечего перенастраивать: тот же адрес, порт, логин и пароль.

- Делает это демон после успешного `netmode-apply b4`
  (`internal/httpapi/b4proxy.go`, `syncB4Proxy`): читает из UCI
  `nikki.mixin.mixed_port`, `nikki.mixin.authentication` и
  `nikki.@authentication[0].username/password`, ждёт API b4, сравнивает с
  `GET /api/socks5/config` и, только если отличается, пишет секцию
  (`POST /api/socks5/config`) и перезапускает b4 (`POST /api/system/restart`).
  Совпадает — ничего не делает: повторное переключение b4 не перезапускает.
- Логин — только если он включён у nikki: иначе b4 требовал бы пароль,
  которого клиенты в режиме nikki не вводили.
- Адрес — `0.0.0.0`, как у mixed-port: к порту приходят и с LAN, и через
  проброс VM.
- **Не валит переключение.** Обход для LAN от SOCKS5 не зависит; сбой
  синхронизации пишется в журнал (`b4 socks5: …`), джоб режима — `done`.
- b4 сохраняет секцию в своём конфиге сам, поэтому b4, поднятый при загрузке
  без демона, слушает тот же порт.

Новые поверхности API b4 (к таблице ADR-0007; `docs/recon/b4-api.md`,
`docs/recon/evidence.json`, живая проба `raw/52-b4-socks5.txt`):

| Вызов | Зачем | Источник |
|---|---|---|
| `GET /api/socks5/config` | прочитать секцию SOCKS5 (пароль отдаётся открытым) | `src/http/handler/socks5.go:13,22-34`, `raw/52-b4-socks5.txt` |
| `POST /api/socks5/config` | заменить секцию ЦЕЛИКОМ — поэтому только «прочитал, поменял, отправил всё» | `socks5.go:43-82` |
| `POST /api/system/restart` | применить: слушатель читает секцию только при старте | `src/http/handler/system.go:19,142-214` |

`PUT /api/config` (замена всего конфига) по-прежнему не используется.

**Почему в Go, а не в `netmode-apply`.** У скрипта нет HTTP-клиента (на
роутере busybox), фиксированный контракт кодов выхода, и «не валить
переключение» в нём выражалось бы новым кодом. У демона уже есть и
`UCIGet`, и клиент b4 с потолком тела и таймаутами.

## Последствия

- **В режиме b4 — только SOCKS5.** HTTP-прокси у b4 нет
  (`socks5/server.go:201-202` отвергает не-SOCKS5 первый байт): `http://`,
  `http_proxy=http://…` и HTTP/HTTPS-прокси macOS в режиме b4 не работают.
  Клиенты, умеющие SOCKS5 (`socks5h://`, поле SOCKS в Firefox, SOCKS-прокси
  macOS), работают в обоих режимах. Приложение `desktop/` следует режиму:
  в b4 убирает HTTP-адрес из копирования, `export` — на `socks5h://`, а
  включённый системный прокси переводит на «только SOCKS» (HTTP и HTTPS
  выключает) и обратно при возврате в nikki.
- Первое переключение на b4 после смены порта или логина у nikki дольше на
  перезапуск b4 (на стенде переключение целиком заняло ~5 с).
- Правка `mixed_port` или логина nikki доезжает до b4 при следующем
  переключении на b4, не мгновенно.
- b4 отвергает занятый порт (preflight, `port_in_use_system`): пока nikki
  держит порт, запись невозможна — поэтому синхронизация идёт только после
  `netmode-apply b4`, когда nikki остановлен.
- Сет b4 с upstream на `127.0.0.1:<тот же порт>` b4 отвергнет как петлю
  (`socks5_loop`, `validation.go:158-161`) — синхронизация тогда упадёт с
  записью в журнал.

## Рассмотренные альтернативы

- **Отдельный порт для b4 (1080).** Клиентам пришлось бы менять порт вместе
  с режимом, а стенду — второй проброс. Против требования владельца.
- **nikki как «прямой» прокси рядом с b4.** Ломает инвариант «один движок»
  (SPEC, `netmode-apply`), и правила nft двух движков в соседстве не
  проверены.
- **Отдельный HTTP-прокси (tinyproxy/microsocks) в режиме b4.** Ещё один
  пакет и служба на роутере ради HTTP; SOCKS5 b4 уже есть в стоящей сборке.
