# ADR-0008: Эксклюзивный выбор сета — наша семантика, а не модель b4

## Статус
Принято — 2026-08-02

> **Сверка с кодом — 2026-08-03.** Решение в силе; ADR задним числом не
> переписывается. Но текст ниже местами описывает как существующее то, чего
> в коде нет. Расхождения правятся кодом, а не этим файлом:
>
> - Клиент шлёт **`id`**, а не имя: `POST /api/b4/set` принимает `{"id": …}`. Резолвинга имени в `id` нет.
> - Следовательно `409 ambiguous_set_name` **не отдаётся никогда** и в коде отсутствует. Он зарезервирован — см. `docs/contracts/errors.md`.
> - `selected` при нуле и при двух и более включённых — пустая строка `""`, а не `null` (`b4.Selected`). Различать случаи следует по `enabled_count`.

## Контекст

В b4 **нет «текущего сета»**. Каждый сет имеет собственный флаг `enabled`
(`src/config/types.go:395`), включённых может быть сколько угодно
одновременно, а порядок в массиве задаёт приоритет обработки
(`docs/recon/b4-api.md`).

SPEC §7 при этом описывает панель в терминах одного выбранного:
`GET /api/b4/sets` — «список сетов и текущий», `POST /api/b4/set {"set":"..."}`.

Это не ошибка спеки, а решение владельца: панель — пульт с переключателем, а
не редактор конфигурации b4. Но расхождение моделей надо зафиксировать, иначе
первый же пользователь b4-морды решит, что панель сломала ему настройки.

## Решение

Панель **навязывает** правило «включён ровно один сет». Это наша семантика,
и она реализуется двумя вызовами:

```
POST /api/sets/batch-set-enabled {"ids": [<все прочие>], "enabled": false}
POST /api/sets/batch-set-enabled {"ids": [<целевой>],    "enabled": true}
```

Порядок именно такой: сначала гасим, потом зажигаем. При обрыве между
вызовами система остаётся в состоянии «ничего не включено» — трафик идёт без
обработки b4, что заметно и безопасно. Обратный порядок в тот же момент дал бы
«включены оба», то есть тихое изменение приоритетов.

Обработка ответа:

- `updated: 0` — **не ошибка** (`sets.go:679-683`): значит запрошенное
  значение уже стояло. Возвращаем успех.
- `404` от b4 (ни один id не найден) → наш `404 not_found`: список устарел,
  клиент должен перечитать.
- Пустой список «прочих» — первый вызов пропускаем, не отправляем пустой
  `ids` (b4 отвечает на него `400`, `sets.go:649-652`).

Чтение состояния зеркально:

| Что видим в `GET /api/sets` | Что отдаём | `selected` |
|---|---|---|
| ровно один `enabled: true` | наш выбор виден | имя сета |
| ноль `enabled` | b4 ничего не обрабатывает | `null`, `enabled_count: 0` |
| два и более `enabled` | эксклюзивность нарушена извне | `null`, `enabled_count: N` |

Последняя строка — не ошибка и не повод «чинить». Показываем как есть, ровно
как с `Ambiguous` для WiFi ([ADR-0010](0010-never-auto-repair.md)). Следующее
нажатие в панели приведёт состояние к одному выбранному.

Клиент шлёт **имя**, не `id`: `id` — UUID, генерируемый сервером
(`sets.go:315`), и может смениться при пересоздании сета; хранить его между
запросами нельзя. Имя резолвится в `id` сканированием свежего `GET /api/sets`
в момент вызова. **`name` не уникален** — если совпало два, возвращаем
`409 ambiguous_set_name` и не угадываем.

## Последствия

**Приобретаем**

- Одна радиокнопка в UI вместо N чекбоксов с неочевидным взаимодействием
  приоритетов.
- Состояние «какой сет активен» читается одним взглядом и одним полем.
- Мы не изобретаем собственного хранилища выбора — правда по-прежнему в b4
  ([ADR-0002](0002-source-of-truth.md)).

**Платим**

- **Если пользователь включил несколько сетов в веб-морде b4, наше
  переключение их погасит.** Это ожидаемое поведение выбранной модели, а не
  баг; оно должно быть написано в UI рядом с переключателем.
- Два HTTP-вызова вместо одного, между ними — окно, в котором активных сетов
  ноль. Для локального вызова это миллисекунды.
- Мы теряем управление приоритетом (порядком) сетов. Панель его не показывает
  и не меняет — для этого есть морда b4.

## Рассмотренные альтернативы

| Вариант | За | Против | Почему не он |
|---|---|---|---|
| Показывать модель b4 как есть (N независимых переключателей) | Честно, ничего не ломает у пользователя b4 | Панель перестаёт быть пультом: нужен UI приоритетов, порядка и объяснение, что значит «включены три» | Решение владельца: пульт, а не второй редактор b4 |
| Эксклюзивность одним вызовом `PUT /api/sets/{id}` | Один запрос | Полная замена, стирает стратегию (`sets.go:351-368`) | Запрещено [ADR-0007](0007-b4-api-only.md) |
| Хранить «наш выбранный сет» у себя и сверять | Устойчиво к правкам извне | Второй источник правды; после правки в морде b4 панель врёт | Нарушает [ADR-0002](0002-source-of-truth.md) |
| Включить целевой, потом погасить прочие | На секунду не остаёмся без обработки | Промежуточное состояние «включены оба» меняет приоритеты и может пропустить трафик не через тот сет | Тихое неверное поведение хуже громкого отсутствия обработки |
