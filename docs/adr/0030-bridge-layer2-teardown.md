# ADR-0030: проброс LAN в uplink — слой 2, вердикт по наблюдению, демонтаж ≠ откат

## Статус
Принято — 2026-09-01. Уточняет [ADR-0015](0015-executor-shape.md): форма
`Executor` не меняется, добавляются именованные глаголы моста со своей
таблицей исходов — по образцу [ADR-0027](0027-netmode-wifi-exit-codes.md).
Опирается на [ADR-0006](0006-no-rollback.md) и
[ADR-0028](0028-uci-revert-not-rollback.md).

## Контекст

Проброс делает ПК за LAN-портом видимым клиентам uplink-сети: VLAN2 на
LAN-порту → интерфейс homelan (br-lan.2, статическая нога в uplink-подсети) →
relayd → wwan. Конфигурация собрана руками и проверена живьём до кода
(docs/recon/raw/80…87); панель делает её включаемой и выключаемой.

Рискованные глаголы (`ubus call network reload`, `/etc/init.d/firewall
reload`, `apk add relayd`, стоп relayd, ping-проба) по SPEC §4 живут только
в скрипте слоя 2 — `/usr/local/bin/netmode-bridge`. uci пишет демон; объект
`network` в ubus-allowlist демона не попадает никогда (прецедент —
upstreamhandler: general reload у демона означал бы general restart).

## Решение

1. **Скрипт слоя 2 `netmode-bridge`** с глаголами `status <port>`,
   `probe <ip> <dev>`, `install`, `apply enable|disable|access` и таблицей
   кодов: 0 выполнено/ответил, 1 misuse, 3 занято (свой flock), 4 применение
   не прошло, 5 relayd не остановился, 7 нет предусловия, 8 probe: адрес не
   ответил, 9 apk add отказал. Код 8 отдельный намеренно: «адрес свободен» —
   то суждение, на потере которого строился живой IP-конфликт 2026-08-31.
   Чтения (status, probe) замка не берут.

2. **Вердикт по наблюдению** (ADR-0002, ADR-0025): скрипт не имеет права
   утверждать, что мост работает, — `network reload` возвращает 0 и при
   конфигурации, ведущей в никуда (VLAN на несуществующем порту, живой
   случай). Судит демон: `ubus call network.interface.homelan status` → up
   с нужным адресом, затем `BridgeStatus` → relayd жив.

3. **Полный демонтаж — это не откат.** `disable` удаляет bridge-vlan,
   homelan, relay, vlan_filtering, зону и форвардинги — и это целевое
   состояние, заказанное владельцем нажатием, а не восстановление снимка
   «как было» (ADR-0006 запрещает второе, не первое). Секции при демонтаже
   ищутся ПО ТИПУ И СОДЕРЖИМОМУ (bridge-vlan с device='br-lan', зона по
   name='homelan'), а не по именам netmode_*: живой роутер уже несёт ручную
   сборку с анонимными секциями, и демонтаж обязан уметь разобрать её.

4. **relayd запускаем не мы.** Процесс поднимает procd-сервис
   `/etc/init.d/relayd` (START=80), читающий секции `network` с
   `proto=relay`; обработчика `/lib/netifd/proto/relay.sh` на роутере нет
   вовсе (raw/88 §7). Второй стартёр однажды разошёлся бы с первым, поэтому
   демон сервис не трогает. У `disable` есть ровно один страховочный стоп по
   живому `pidof` — лестницы из kill нет (ADR-0025).

   Формулировка исправлена 2026-09-02: прежняя приписывала запуск netifd.
   Ошибка была безобидной по последствиям, но вводила в заблуждение ровно
   там, где объясняется страховочный стоп.

5. **Uplink-подсеть выводится из живого статуса wwan на каждый запрос.**
   Во время разведки роутер был подключён уже к другой сети (raw/86: шлюз
   10.124.199.136) при живой ноге 192.168.0.85 — запомненная подсеть врёт.

6. **Включение чинит МАРШРУТИЗАЦИЮ, а не только firewall.** После
   включения в главной таблице две записи о uplink-подсети — через
   станционный интерфейс и через ногу моста, — и для транзитного пакета из
   LAN ядро выбирает станционный: пакет к ПК уходит в эфир uplink, где ПК
   нет. Собственные таблицы relayd не помогают: его правила смотрят только
   на два мостуемых интерфейса, а пакет из LAN приходит на третий (raw/88).

   Ставятся две вещи, и они делят работу:

   - `config route` через `homelan` на `/32` адрес ПК — детерминированный
     пол: адрес известен, потому что владелец его ввёл;
   - две секции `config rule` (`in='lan'`, `lookup` в базу таблиц relayd и
     базу+1, приоритеты 3 и 4) — покрывают ВСЁ, что relayd выучил, включая
     виртуалки на ПК, чьих адресов панель не знает и знать не может.

   Правил два, потому что relayd кладёт хосты одной стороны моста в базу,
   другой — в базу+1, и какая сторона куда попадёт, зависит от порядка
   получения интерфейсов; просмотр обеих снимает зависимость от порядка.
   База (16800) не пиннится через `option table`: relayd — отдельный
   procd-сервис, и `network reload` его не перезапускает, так что пин
   потребовал бы расширить глагол скрипта. Значение объявлено собственной
   validate-схемой relayd и процитировано в evidence.

   Всё это ставится при ВКЛЮЧЕНИИ, а не вместе с доступом из точки доступа:
   маршрутизация отвечает на вопрос «где живут эти хосты», доступ открывает
   firewall — одно правило, один смысл.

   **Известная граница:** если relayd когда-нибудь сменит базу таблиц по
   умолчанию, правила будут указывать в пустоту — молча, без отказа.
   Доступ к самому ПК это переживёт (его держит `/32`), доступ к виртуалкам
   из Wi-Fi роутера — нет.

7. **`masq_src` с отрицанием** — подтверждено: `'!192.168.0.0/24'` fw4
   компилирует в `ip saddr != … masquerade` (raw/85). Транзит uplink↔ПК
   ходит без NAT, клиенты LAN NAT-ятся как раньше.

## Последствия

- Установка relayd — только по явному согласию владельца (`install:true` в
  запросе после вопроса панели); отказ означает «не сделано ничего».
- Пять мест таблицы кодов (шапка скрипта, executor.go, contracts/executor.md,
  этот ADR, check-netmode-bridge.sh) синхронизируются руками — гвард гоняет
  только пару «скрипт ↔ сценарии» (оговорка ADR-0027 дословно).
- `check-netmode-bridge.sh` в `make verify` держит поведение скрипта.
