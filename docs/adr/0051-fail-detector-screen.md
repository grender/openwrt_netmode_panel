# ADR-0051: Детектор отказов — четвёртый экран и проверка звеньев по кнопке

## Статус

Принято 2026-11-17. Дополняет [ADR-0043](0043-device-traffic-watch.md)
(экран читает ту же сессию наблюдателя) и
[ADR-0050](0050-exit-chains-via-subscription.md) (проверяются его цепочки).
Ничего не отменяет.

## Контекст

17.11.2026 искали, почему трафик, отправленный в `EXIT-KZ-RESI`, иногда
выходит с домашнего IP. Причина — правило с узлом без UDP mihomo пропускает
([ADR-0049](0049-exit-groups-as-set-targets.md), исправление там же) — нашлась
руками: Clash API, `jq`, ssh. В панели не было места, где видно сразу все
пути и хоп, на котором рвётся связь. «Наблюдатель» показывает запросы одного
устройства, но только два конца цепочки (`группа[узел]`) и без схемы.

Нужно: схема по хопам — клиент, роутер, активные серверы подписки, свои
ноды, ISP-прокси — и звено, на котором рвётся.

## Решение

### Экран `#fails`, только чтение

Четвёртый экран, вход — строка на полке главной в режиме nikki. Ничего не
переключает: выбор пути остаётся в карточке Nikki («Свои выходы»).

Сверху — граф столбцами: устройство → роутер → серверы подписки → свои
ноды → выходы (IP сервера подписки, IP VPS, ISP-прокси, домашний IP) →
интернет. Ребро зелёное, красное или серое пунктирное («не проверено»);
жирное — по нему сейчас идёт какой-то маршрут. Ниже — маршруты: группа,
текущий путь по звеньям, что в неё направлено, и запросы устройства.

«Активные» серверы подписки — хопы пула и узел, на котором стоит `PROXY`.
Все узлы подписки на схему не выносятся: их десятки, и к вопросу «где
рвётся» отношения не имеют.

### Карта и диагноз — в панели

Граф собирает `state/routemap.ts` из того, что панель уже получает:
`/api/nikki/rulesets`, `/api/nikki/exits`, `/api/nikki/hops`,
`/api/nikki/proxies` и сессия `/api/watch`. Вывод о виновнике делается там
же: демон отдаёт замеры, а не диагноз.

- `resi` не ответил при дошедшем `dc` той же ноды → красное «нода → ISP-прокси»;
- цепочка не ответила при живом хопе → красное «хоп → нода»; при мёртвом
  хопе это звено серое: красный уже хоп;
- выход не ответил, а до ноды не дошли ни одним путём → звено за нодой серое.

Запрос устройства ложится на маршрут по цепочке из наблюдателя
(`error_chain` у отказавшего, иначе `chain`). Отказы маршрута приписываются
его красному звену; красного нет — первому непроверенному.

### `POST /api/nikki/pathtest` — по кнопке

Панель не знает трёх вещей: дошёл бы роутер до ноды напрямую, жива ли
цепочка через каждый хоп, отвечает ли выход за нодой. Их меряет один
синхронный запрос теми же пробами Clash API, что и `POST /api/nikki/test`:

| Звено | Узел | Таймаут |
|---|---|---|
| роутер → сервер подписки | хоп пула, узел туннеля | 1,5 с |
| роутер → нода | `<нода>-dc` | 1,5 с |
| хоп → нода | `<нода>-dc ⇢ <хоп>` | 1,5 с |
| нода → ISP-прокси | `<нода>-resi`, одна проба на ноду | 8 с |

Выход `dc` — freedom на VPS, поэтому его проба и есть проба дороги до ноды.
Проба `resi` идёт после остальных: прямой путь мёртв, а цепочка через хоп
повторителя жива — пробуется `⇢ авто`, иначе «не дошли до ноды» читалось бы
как «отказал прокси».

**Только по нажатию.** ISP-прокси отказывает на частых новых соединениях
([ADR-0050](0050-exit-chains-via-subscription.md), хоп для resi выбирается
по замерам dc по той же причине). Фоновая или автоматическая проба при
открытии экрана била бы по нему каждый заход.

Длинный таймаут — отдельным необязательным интерфейсом `nikki.TimedProber`,
а не методом `nikki.Client`: нужен одному вызывающему, а `Client` реализуют
все подделки. Пути Clash API те же, что уже сняты разведкой.

## Последствия

- Отказы запросов — только выбранного в наблюдателе устройства и только
  пока идёт сессия. Прошлых отказов экран не знает.
- Открытый детектор продлевает сессию наблюдателя, как сам наблюдатель.
- Проба — `generate_204` по TCP: UDP и конкретный домен не проверяются.
  Утечку вида «UDP мимо выхода» экран покажет только по факту — запросом
  устройства на маршруте «Напрямую».
- Красное «нода → ISP-прокси» значит «прокси или путь от ноды до него»:
  точнее с роутера не видно.
- Какой набор совпал бы у домена, по которому нет трафика, неизвестно:
  содержимого наборов у демона нет.
- Несколько нод под одной группой `EXIT-*`: какая выбрана, панель не
  знает — путь маршрута не рисуется, рёбра остаются.
- Тестов логики панели нет, как и остальных фронтенд-тестов; обработчик
  покрыт `internal/httpapi/pathtest_test.go`.

## Рассмотренные альтернативы

- **Фоновая память отказов в демоне** (кольцо за последний час по всем
  устройствам). Единственный вариант, который показал бы уже случившееся,
  но это постоянный поток `/logs` уровня info и опрос `/connections` на
  роутере. Владелец выбрал сессию наблюдателя.
- **Вписать схему в «Наблюдатель».** Тот экран отвечает на вопрос «что
  просит устройство», и схема путей нужна и без устройства.
- **Проба при открытии экрана.** Отвергнута из-за ISP-прокси, см. выше.
- **Спрашивать у mihomo, какое правило совпадёт с доменом.** Потребовало
  бы новой разведки Clash API и записи в `evidence.json`; вопрос экрана —
  «где рвётся», а не «куда пошло бы».
