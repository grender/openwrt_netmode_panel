# ADR-0015: `Executor` без универсального `Run`; парсеры — чистые функции

## Статус
Принято — 2026-08-02. **Отменяет интерфейс из SPEC §10.** Уточнён
[ADR-0031](0031-subscription-in-daemon.md) (2026-09-03): глагол
`UpdateSubscription`, упомянутый ниже как метод интерфейса, удалён — у него
больше нет адресата на роутере; текст не переписан.

> **Сверка с кодом — 2026-08-03.** Решение в силе; ADR задним числом не
> переписывается. Но текст ниже местами описывает как существующее то, чего
> в коде нет. Расхождения правятся кодом, а не этим файлом:
>
> - Фикстуры `iwinfo scan` и `iwinfo info` **сняты** (`raw/23`, `raw/24`), `wireless.ParseScan` и `wireless.ParseInfo` написаны и покрыты тестами на них. Пометки «отсутствует, NEEDS RECON» ниже устарели.
> - Все методы интерфейса принимают `context.Context` первым аргументом — в блоке ниже он опущен для краткости.
> - У `ApplyMode` появилась таблица исходов (`ErrApplyBusy`, `ErrApplyFirewall`, `ErrApplyStart`, `ErrApplyVerify`, `ErrApplyPrereq`) — [ADR-0020](0020-netmode-apply-exit-codes.md). Форма интерфейса при этом не изменилась, что и было условием.

## Контекст

SPEC §10 задаёт интерфейс:

```go
type Executor interface {
    UCIGet(pkg, section, option string) (string, error)
    UCISet(pkg, section, option, value string) error
    UCICommit(pkg string) error
    Service(name, action string) error
    SnapshotConfigs() (string, error)
    RestoreConfigs(path string) error
    WifiScan(device string) ([]Network, error)
    Run(cmd string, args ...string) ([]byte, error)
}
```

Он не выдерживает столкновения с задачей:

1. `UCIGet` возвращает одну опцию по точному адресу. **Перечислить секции им
   невозможно** — а классификация выбора требует именно перечисления всех
   `wifi-iface` с `device=radio0`.
2. Нет удаления опции и секции, нет создания именованной секции — а
   `POST` и `DELETE /api/wifi/networks` требуют и того, и другого.
3. Нет чтения стейджинга — а без него наш `uci commit` опубликует чужой
   черновик ([ADR-0011](0011-optimistic-concurrency.md)).
4. `SnapshotConfigs`/`RestoreConfigs` отменены ([ADR-0006](0006-no-rollback.md)).
5. `WifiScan` возвращает **разобранные** структуры — значит парсер оказался за
   интерфейсом и в тестах подменяется вместе с ним. Тестировать парсер станет
   нечем, кроме живого роутера.
6. `Run(cmd, args...)` даёт неограниченные полномочия. Через него `tar` для
   снапшота, прямой `/etc/init.d/b4 restart` в обход `netmode-apply` и любой
   другой обход границы возвращаются одной строкой, и никакой грепающий
   скрипт этого не поймает.

## Решение

Интерфейс перечисляет **все** полномочия демона над системой и содержит
только глаголы, которые действительно нужны. Ни одного универсального.
Полные сигнатуры и обоснование каждого метода —
[`docs/contracts/executor.md`](../contracts/executor.md).

Ключевые изменения относительно SPEC §10:

| Изменение | Почему |
|---|---|
| `UCIShow(pkg) ([]byte, error)` добавлен | единственный способ перечислить секции; отдаёт **сырые байты**, разбор снаружи |
| `UCIDelete`, `UCIAddNamed` добавлены | без них нет `POST`/`DELETE` сетей |
| `UCIChanges(pkg)` добавлен | защита от публикации чужого стейджинга |
| `UbusCall(object, method, args)` добавлен, отдаёт сырой JSON | одна дверь к ubus вместо метода на каждый вызов |
| `WifiScan` **удалён** | стал чистой функцией `wireless.ParseScan([]byte)` над результатом `UbusCall` |
| `SnapshotConfigs`, `RestoreConfigs` **удалены** | [ADR-0006](0006-no-rollback.md) |
| `Service(name, action)` **удалён** | сервисы стартует только `netmode-apply` (SPEC §4, Слой 2). Метод позволял бы обойти это правило |
| `Run(cmd, args...)` **удалён** | заменён двумя именованными глаголами: `ApplyMode`, `UpdateSubscription` |
| `UCIRevert` **не добавлен** | откат чужого стейджинга уничтожает чужую работу ([ADR-0011](0011-optimistic-concurrency.md)) |
| `MissingExecutors() []string` добавлен | единственный метод, который ничего не выполняет, и осознанное исключение из «интерфейс перечисляет полномочия». Полномочие тут одно — посмотреть на собственные руки. Пути скриптов слоя 2 знал конструктор, а проверить их было негде: демон отдавал панель с кнопками, которые заведомо не могли сработать, и узнавал об этом вместе с владельцем — после `uci commit`, когда намерение уже опубликовано и ждёт применения. Измерено на живом роутере, см. `ErrNoExecutor` в [контракте](../contracts/executor.md) |

**Правило разбора.** Всё, что приходит от системы, пересекает интерфейс в виде
`[]byte`. Разбор — чистые функции в круге 1 ([ADR-0001](0001-layering.md)):

| Функция | Вход | Фикстура для теста |
|---|---|---|
| `uci.ParseShow` | вывод `uci show <pkg>` | `raw/10-uci-show-wireless.txt`, `raw/11-uci-show-network.txt` |
| `wireless.ParseStatus` | `network.wireless status` | `raw/21-ubus-network-wireless-status.json` |
| `wireless.ParseScan` | `iwinfo scan` | **отсутствует, NEEDS RECON** |
| `wireless.Classify` | результат `ParseShow` | те же |
| `wireless.Fingerprint` | сырой вывод `uci show wireless` | те же |

Эти функции тестируются **без единого мока**: на входе байты, записанные с
живого роутера. Рукописный мок проверяет нашу догадку саму против себя;
записанный вывод ловит ошибки формы — например, экранирование в
`REDACTED_PSK!!SPECIAL@@` (`raw/10-uci-show-wireless.txt:41`).

> **NEEDS RECON** — фикстуры вывода `iwinfo scan` и `iwinfo info` нет вовсе;
> известны только сигнатуры вызовов (`raw/22-ubus-v-list-iwinfo.txt`), но не
> имена полей ответа. `ParseScan` и `ParseInfo` нельзя писать до ответа.
> Разрешается:
> `ubus call iwinfo scan '{"device":"phy0.0-sta0"}'`
> `ubus call iwinfo info '{"device":"phy0.0-sta0"}'`

## Последствия

**Приобретаем**

- Интерфейс на один экран — это исчерпывающий список того, что демон вообще
  может сделать с роутером. Проверка изменений сводится к чтению `diff`
  интерфейса.
- Парсеры (самый ошибкоопасный код) тестируются на настоящем выводе роутера,
  без моков и без сети.
- Обойти `netmode-apply` или вернуть tar-снапшот нельзя «по-тихому»: нужен
  новый метод интерфейса, а это заметно в ревью.
- Фейковая реализация тривиальна: несколько `map[string][]byte` из
  `docs/recon/raw/`.

**Платим**

- Каждое новое системное действие — правка интерфейса, реализации и фейка.
  Три файла вместо одной строки `exec.Command`. Это и есть цель, но это цена.
- `ApplyMode` и `UpdateSubscription` — «узкоспециальные» методы, которые в
  чистом виде архитектуре не нравятся. Альтернатива (`Run`) хуже.
- `MissingExecutors` пробивает правило «интерфейс — это глаголы»: он ничего
  не делает с системой, только смотрит. Держать его снаружи, обычным
  `os.Stat` в `internal/httpapi`, было бы чище по форме и хуже по существу —
  пути живут в `executor.Exec`, и вторая их копия в вызывающем разъехалась бы
  молча. Исключение записано здесь, чтобы следующий «просто посмотреть» метод
  добавляли с тем же доводом или не добавляли вовсе.
- Сырые `[]byte` через интерфейс означают разбор на стороне вызывающего и
  чуть больше кода в местах использования.
- `UbusCall` остаётся довольно широкой дверью: объект и метод — строки. Сузить
  её механически нечем, кроме `scripts/check-evidence.sh`, который требует,
  чтобы имя объекта было процитировано в `evidence.json`.

## Рассмотренные альтернативы

| Вариант | За | Против | Почему не он |
|---|---|---|---|
| Интерфейс SPEC §10 как есть | Написан, знаком | Не выражает половины нужного; `Run` открывает всё; `WifiScan` уносит парсер за мок | Не выдерживает задачи |
| Только `Run` + всё остальное поверх | Минимальный интерфейс, максимум гибкости | Мок должен понимать командные строки — то есть повторять систему; ни один гейт не работает | Мокабельность превращается в фикцию |
| Метод на каждый вызов ubus (`WirelessStatus`, `IwinfoScan`, …) | Типобезопасно, узко | Интерфейс растёт с каждым запросом, фейк — вместе с ним; разница с `UbusCall` только в месте склейки строки | Не окупается при 3–4 вызовах |
| Разбор внутри `Executor`, наружу — структуры | Удобно вызывать | Парсер за моком → тестируется только на роутере. Это ровно та ошибка, из-за которой удалён `WifiScan` | Противоречит цели SPEC §10 |
