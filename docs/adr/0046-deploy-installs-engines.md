# ADR-0046: `deploy.sh --install` ставит nikki и b4 по версиям из репозитория

## Статус

Принято 2026-09-25. Дополняет [ADR-0045](0045-vm-test-rig.md): его решение
«nikki и b4 в VM не ставятся — их установка будет делом deploy.sh»
выполнено. Ничего не отменяет.

## Контекст

`deploy.sh --install` предполагал, что nikki, b4 и `flock` на роутере уже
стоят: владелец ставил их руками. На ванильном OpenWrt 25.12 деплой падал
первой же проверкой (нет `flock`), а в тестовой VM без nikki обновление
подписки скачивало узлы и отказывало на записи
`/etc/nikki/run/providers/sub.yaml`: каталога нет, и `atomicfile` нарочно
его не создаёт. Воспроизвести роутер с нуля было нечем, а стенд из ADR-0045
не мог проверить ни движки, ни подписку, ни наборы.

Ограничения, выясненные разведкой
([docs/recon/raw/98-engines-fresh-install-vm.txt](../recon/raw/98-engines-fresh-install-vm.txt)):

- фид nikki (`nikkinikki.pages.dev`) и `releases/download` GitHub с роутера
  не открываются; с Mac GitHub открывается;
- у OpenWrt-nikki есть версионные релизы на GitHub: один архив на
  архитектуру, внутри — локальный фид с `.apk`, у архива опубликован sha256.
  Релиз `v1.26.1` — ровно версии роутера (nikki 2026.04.08-r1,
  luci-app-nikki 1.26.1-r1); архитектуры у роутера и VM разные
  (`aarch64_cortex-a53` и `aarch64_generic`);
- у nikki свой ключ подписи, в `/etc/apk/keys` его нет;
- postinst nikki службу включает (`S99nikki`), но не запускает: у пакета
  свой выключатель `nikki.config.enabled='0'`, и при нём `init.d start`
  молча ничего не делает — `netmode-apply nikki` падал бы кодом 6;
- профиль выбирается строкой `nikki.config.profile='file:<имя>'`, по
  умолчанию — подписка-заглушка пакета; `profiles/` пуст;
- mihomo идёт под root, `run/` при старте не чистится, без `sub.yaml`
  mihomo стартует (ошибка провайдера только в журнале);
- демон читает `api_secret` nikki при старте: поднятый раньше установки
  nikki, он получает «секрет отвергнут» до следующего рестарта;
- b4 — один статический бинарь в релизе GitHub, init.d апстрим пишет своим
  установщиком, `b4.json` b4 создаёт сам при первом старте.

## Решение

**Движки ставит `--install`, без отдельного флага.** Фаза «Движки» идёт до
заливки демона — отказ в ней оставляет роутер с прежним демоном — и до его
перезапуска: демон стартует уже с `api_secret`.

**«Стоит — не трогаем».** Движок считается установленным по тем же
признакам, по которым им пользуется `netmode-apply`: есть `/etc/init.d/<движок>`
и его ядро. Тогда не трогаются ни пакеты, ни `/etc/config/nikki`, ни профиль,
ни `b4.json`, а расхождение с закреплённой версией — только предупреждение.
Половинчатое состояние (init.d без ядра или наоборот) — состояние владельца:
предупреждение, не чиним ([ADR-0010](0010-never-auto-repair.md)). На роутере,
где всё поставлено руками, фаза — пустой проход без вызова apk;
`scripts/engines-plan.sh` показывает это заранее, только читая роутер.

**Версии закреплены в `scripts/engines.lock`**: тег релиза, архитектура,
имя архива и sha256. Стенд и роутер получают одно и то же; обновление —
осознанная правка файла. Архивы качаются на Mac (кэш `build/engines/`),
сверяются с lock до первого изменения на роутере и заливаются через
`ssh cat` — sftp в dropbear нет.

**nikki ставится `apk add --allow-untrusted`** из файлов архива: `nikki`,
`mihomo-meta`, `luci-app-nikki`, `luci-i18n-nikki-ru`; зависимости — из
штатного фида. Целостность даёт sha256 из git, а не ключ nikki: положить
ключ в `/etc/apk/keys` значило бы доверить третьей стороне все будущие
установки, и сам ключ пришлось бы брать с недоступного с роутера хоста.

**Включением движков владеет `netmode-apply`.** Сразу после установки
служба nikki останавливается и выключается, b4 ставится выключенным. На
свежем nikki включается его собственный выключатель `config.enabled=1` —
иначе `netmode-apply nikki` не смог бы его запустить; работает движок по-прежнему
только в выбранном режиме.

**Профиль — шаблон, только если своего нет.** Пустой `/etc/nikki/profiles` —
кладётся `files/etc/nikki/profiles/netmoded.yaml` (провайдеры `sub`/`sub-auto`,
группы `AUTO`/`PROXY`/`BYPASS`, `MATCH,DIRECT` — контракт
[docs/contracts/nikki-mixin-rulesets.md](../contracts/nikki-mixin-rulesets.md))
и выбирается в `/etc/config/nikki`. Дальше он владельца. Демон профиль
по-прежнему не пишет ([ADR-0002](0002-source-of-truth.md)): его кладёт
установщик и один раз. `nikki.mixin.api_listen` и `ui_path` дописываются,
только если пусты; `api_secret` генерирует пакет, установщик его не выдумывает.

**`/etc/nikki/run/providers` создаёт установщик**, если его нет (пакет
создаёт сам, но каталог могли удалить). Это не расходится с отказом
`atomicfile` создавать каталоги: там довод — «нет каталога, значит его
владелец не развёрнут», а установщик и есть тот, кто развёртывает.

**b4 — свой init.d по шаблону апстрима** (`files/etc/init.d/b4`, из
`installer/services/procd.sh` b4 v1.74.1): бинарь `/usr/bin/b4`, конфиг
`/etc/b4/b4.json`, без `enable`. Установщик апстрима не запускается: он
интерактивный, качает с GitHub и сам выбирает `/opt` или USB. `b4.json` не
пишется ([ADR-0007](0007-b4-api-only.md)). Недостающие kmod (`kmod-nft-queue`
и др.) и `flock` ставятся из штатного фида одним вызовом apk.

**Вывод и журнал.** Шаги деплоя пронумерованы, отказ печатает, что не
вышло, в каком состоянии роутер и что набрать. Полный вывод `--install`
пишется в `build/deploy-logs/` (токен панели скрыт; адрес подписки и
`api_secret` не печатаются вовсе), изменения на роутере — ещё и в его
журнал с тегом `netmoded-deploy`.

## Отвергнуто

- **Отдельный флаг `--engines`.** Два пути установки расходятся, а свежая
  система без движков — не особый случай, а исходный.
- **Скользящий фид `nikkinikki.pages.dev`.** Отдаёт только последнюю
  версию — закрепить нечего; с роутера недоступен, в день разведки — и с Mac.
- **Ключ nikki в `/etc/apk/keys`.** См. выше.
- **Установщик b4 апстрима на роутере.** См. выше.
- **Установка движков в `scripts/vm/provision.sh`.** Стенд проверял бы свою
  установку, а не ту, что поедет на роутер (довод ADR-0045).

## Последствия

- На VM проверяется весь путь: установка движков, режимы off/nikki/b4,
  подписка до «ok», наборы. `provision.sh` больше не ставит `flock` — его
  ставит деплой, и стенд это проверяет. Корень образа VM (~100 МБ) под
  движки мал: одно ядро mihomo — 42 МБ. `fetch-image.sh` растягивает диск
  до `VM_DISK_SIZE` (512 МБ), `provision.sh` — раздел и ext4.
- На роутере `--install` движки не трогает; расхождение версий
  (mihomo 1.19.29 из фида против закреплённого 1.19.27) — предупреждение.
- Обновление движков деплоем не делается: сменить версию — это снести
  пакет руками и поставить заново `--install`, либо обновить руками.
- Не проверяется и на VM: действие b4 на реальном DPI, поведение
  cortex-a53, профиль владельца. geodata и zashboard mihomo качает с GitHub
  при первом старте — на устройстве без доступа к GitHub они не появятся.
- `check-engines` стережёт lock, шаблон профиля и init.d b4.
